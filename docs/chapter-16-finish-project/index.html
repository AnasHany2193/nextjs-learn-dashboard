STEP 02Make search stream, not block

app/dashboard/customers/page.tsx app/ui/customers/table.tsx app/ui/skeletons.tsx

Right now the page awaits the query before rendering anything. Every keystroke blanks the screen until Postgres answers — the exact waterfall the invoices chapter taught you to break with <Suspense>.

So wrap the table in a boundary. Except the table looks like this:

app/ui/customers/table.tsxcurrent
<div className="w-full">
  <h1>Customers</h1>
  <Search placeholder="Search customers..." />   ← inside the table
  <div className="mt-6 flow-root">
    …rows…
This is the trap

The search input lives inside the component you're about to suspend. Wrap this in <Suspense> and every keystroke swaps the whole subtree — input included — for the fallback. React unmounts the real input, so the field loses focus and your cursor after one character. It looks like a debounce bug. It isn't.

The fix is structural: anything that must survive the reload goes outside the boundary. Hoist the heading and the search box into the page, and give the table the query so it can fetch its own data — the same shape app/dashboard/invoices/page.tsx already uses.

app/dashboard/customers/page.tsxedit
return (
  <div className="w-full">
    <h1 className={`${lusitana.className} mb-8 text-xl md:text-2xl`}>
      Customers
    </h1>

    <Search placeholder="Search customers..." />

    {/* key remounts the boundary so the skeleton shows on every new query */}
    <Suspense key={query} fallback={<CustomersTableSkeleton />}>
      <CustomersTable query={query} />
    </Suspense>
  </div>
);

The table now owns its fetch. Its signature changes from a prop to a query, and the three things you hoisted come out of its JSX.

Last piece: the fallback. Model it on InvoicesTableSkeleton, but the customers table has five data columns — Name, Email, Total Invoices, Total Pending, Total Paid.

Count the cells twice

A skeleton is a table too. If its <thead> declares six columns and its row component only renders five <td>, the loading state is visibly one column short of the real thing — and nothing in TypeScript or the linter will tell you. Come back and re-count after step 08 adds the actions column.

Checkpoint

Type slowly in the search box. The skeleton appears while rows load, the heading never flickers, and the cursor stays in the input the whole time. If focus jumps out after one character, something is still inside the boundary that shouldn't be.

STEP 04Paginate — and the count bug

Build it anyway — step 06 is about to break the tie

Six customers at six per page is exactly one page, so pagination is unverifiable today. It stops being unverifiable the moment you create a seventh customer, which is precisely what step 06 does. Build the pagination now, then come back and confirm it after your first create.

The alternative — seed more rows first — works too. What doesn't work is building it, seeing one page, and calling it done.

Give fetchFilteredCustomers a currentPage, add LIMIT/OFFSET, write fetchCustomersPages, and key the boundary on query + currentPage the way the invoices page does.

Move Pagination up a level

Pagination lives in app/ui/invoices/ but has nothing invoice-specific in it — it reads usePathname() and rewrites a page search param. Two consumers now, so git mv it to app/ui/pagination.tsx.

Then copy fetchInvoicesPages as the model for the count query — and read what you copied, because this is where it goes wrong:

app/lib/data.tsthe bug
export async function fetchCustomersPages(query: string) {
  const data = await sql`SELECT COUNT(*)
  FROM customers`;          ← query is never used

  return Math.ceil(Number(data[0].count) / ITEMS_PER_PAGE);
}
Reproduce it

Once you have seven customers, search for a name that matches one of them. The table filters to a single row; the pager still offers two pages, and page 2 renders empty. The row query filters and the count query doesn't, so they disagree the moment you type.

TypeScript already knows: 'query' is declared but its value is never read. An unused parameter on a function whose entire job is filtering is the compiler telling you the filter is missing.

app/lib/data.tsfix
const data = await sql`SELECT COUNT(*)
  FROM customers
+ WHERE
+   customers.name ILIKE ${`%${query}%`} OR
+   customers.email ILIKE ${`%${query}%`}
`;

While you're there, the copied catch still says "Failed to fetch total number of invoices." Fix the noun. Error messages that lie about which table they came from cost you an afternoon eventually. Same goes for the <Search placeholder="Search invoices..." /> that tends to ride along on the customers page.

STEP 05Two components the forms need

app/ui/customers/avatar.tsx app/ui/customers/avatar-picker.tsx

Both forms in the next two steps need to deal with a customer's picture, and the schema makes that harder than it looks. Build these first, once, and the create and edit forms become almost identical.

app/seed/route.tsreference
CREATE TABLE IF NOT EXISTS customers (
  id        UUID DEFAULT uuid_generate_v4() PRIMARY KEY,
  name      VARCHAR(255) NOT NULL,
  email     VARCHAR(255) NOT NULL,   ← note: no UNIQUE
  image_url VARCHAR(255) NOT NULL    ← NOT NULL, and you have no uploader
);

The seeded customers point at six local files in public/customers/. This app has no file upload. So what does a new customer get?

Not an arbitrary URL

Accepting any URL is the tempting answer and the wrong one: next/image refuses any host not listed in images.remotePatterns, and opening that up turns your image optimizer into a fetcher for URLs strangers control. Take the narrow option — offer the six pictures that exist, or none at all.

CustomerAvatar — the fallback

"Or none at all" means image_url can be an empty string, and <Image src=""> throws at render. One component keeps that decision in a single place instead of scattered across the table's desktop and mobile layouts:

app/ui/customers/avatar.tsxnew
function initialsOf(name: string) {
  return name
    .split(" ")
    .filter(Boolean)
    .slice(0, 2)
    .map((part) => part[0].toUpperCase())
    .join("");
}

export default function CustomerAvatar({
  name,
  imageUrl,
  size = 28,
}: {
  name: string;
  imageUrl: string;
  size?: number;
}) {
  if (imageUrl) {
    return (
      <Image
        src={imageUrl}
        className="rounded-full"
        alt={`${name}'s profile picture`}
        width={size}
        height={size}
      />
    );
  }

  // Customers created without a picture fall back to initials.
  return (
    <span
      aria-hidden="true"
      style={{ width: size, height: size, fontSize: size * 0.4 }}
      className="flex shrink-0 items-center justify-center rounded-full
                 bg-blue-100 font-medium text-blue-700"
    >
      {initialsOf(name)}
    </span>
  );
}

Then replace both raw <Image> blocks in table.tsx with it. Do this before step 06, not after — the first customer you create without a picture will otherwise crash the list page you just built.

Why width and height are not optional

next/image requires explicit dimensions (or fill) so it can reserve space and avoid layout shift. Omitting them isn't a warning — it's a runtime error. Passing size through to both the Image and the fallback span keeps the two branches the same size, which is the whole point of a fallback.

AvatarPicker — and why it isn't a <select>

A native select cannot show images

<option> renders as plain text in every browser. Put an <img> inside one and Chrome, Firefox and Safari all strip it — this is specified behaviour, not a bug you can style around. If you want a thumbnail next to each choice, you are building a custom listbox. There is no shortcut.

The pattern: a trigger button that shows the current choice, a role="listbox" panel of options, and a hidden input that carries the value into the form. That hidden input is the important part — it means the server action and the Zod schema never learn that this isn't an ordinary field.

app/ui/customers/avatar-picker.tsxnew
"use client";

// The six pictures the course seeds into public/customers.
const AVATARS = [
  "amy-burns.png",
  "balazs-orban.png",
  "delba-de-oliveira.png",
  "evil-rabbit.png",
  "lee-robinson.png",
  "michael-novotny.png",
].map((file) => ({
  value: `/customers/${file}`,
  label: file.replace(".png", "").replace(/-/g, " "),
}));

export default function AvatarPicker({
  name,
  defaultValue = "",
  error,
}: {
  name: string;
  defaultValue?: string;
  error?: string[];
}) {
  const [value, setValue] = useState(defaultValue);
  const [open, setOpen] = useState(false);
  const listboxId = useId();
  const triggerRef = useRef<HTMLButtonElement>(null);

  const selected = AVATARS.find((a) => a.value === value);

  function choose(next: string) {
    setValue(next);
    setOpen(false);
    triggerRef.current?.focus();   // return focus, don't strand it
  }

  return (
    <div className="relative">
      {/* the bridge: the form sees a normal field */}
      <input type="hidden" name={name} value={value} />

      <button
        ref={triggerRef}
        id={name}              // so the label's htmlFor lands somewhere real
        type="button"          // or it submits the form
        aria-haspopup="listbox"
        aria-expanded={open}
        aria-controls={listboxId}
        onClick={() => setOpen((o) => !o)}
        onKeyDown={(e) => { if (e.key === "Escape") setOpen(false); }}
      >
        {selected ? <Image src={selected.value} … /> : <span>—</span>}
        <span>{selected ? selected.label : "No picture (use initials)"}</span>
        <ChevronUpDownIcon />
      </button>

      {open && (
        <ul id={listboxId} role="listbox" aria-label="Choose a picture">
          {/* "no picture" first, then one option per avatar */}
          <li
            role="option"
            aria-selected={value === ""}
            tabIndex={0}
            onClick={() => choose("")}
            onKeyDown={(e) => {
              if (e.key === "Enter" || e.key === " ") {
                e.preventDefault();
                choose("");
              }
            }}
          >…</li>
        </ul>
      )}
    </div>
  );
}
Four details that are easy to miss
  • type="button" on the trigger. A bare <button> inside a form defaults to type="submit", so opening the picker would submit the form.
  • id={name} on the trigger, so the field's <label htmlFor="imageUrl"> points at something focusable. A label pointing at a hidden input does nothing.
  • triggerRef.current?.focus() after choosing. The panel unmounts on select; without this, keyboard focus falls back to <body> and the user loses their place.
  • e.preventDefault() in the Space handler, or the page scrolls underneath the open panel.

Taking defaultValue as a prop is what lets step 07 reuse this unchanged: create passes nothing, edit passes customer.image_url.

Three ways this insert goes wrong

Copying from createInvoice and editing by hand invites all three at once: writing to users instead of customers, using the JS-side name imageUrl instead of the column image_url, and pasting CREATE TABLE syntax like id UUID DEFAULT uuid_generate_v4() PRIMARY KEY into the VALUES list. That last one fails with syntax error at or near "UUID", and because the whole insert sits in a try, all you see in the browser is the generic "Database Error" message.

That generic message is why the console.error(error) matters. Without it the real Postgres error never reaches you.

Then the form. Three fields, the third being <AvatarPicker name="imageUrl" error={state.errors?.imageUrl} />, plus CreateCustomer in a new buttons.tsx dropped next to the search box, and a create/page.tsx rendering breadcrumbs and the form.

Check the labels you copied

The invoice form's fields are customer, amount and status. Copy it and you get three labels all reading htmlFor="amount", pointing at an id that doesn't exist on this page — so clicking "Name" or "Email" focuses nothing. The accessibility chapter you already did is the one that teaches why that matters.

STEP 08Delete — and the missing foreign key

app/lib/actions.ts app/ui/customers/buttons.tsx app/ui/customers/table.tsx

Delete is three lines of SQL and the most dangerous step in the chapter. Look at what the invoices table declares:

app/seed/route.tsreference
CREATE TABLE IF NOT EXISTS invoices (
  id          UUID DEFAULT uuid_generate_v4() PRIMARY KEY,
  customer_id UUID NOT NULL,     ← no REFERENCES customers(id)
  amount      INT NOT NULL,
  status      VARCHAR(255) NOT NULL,
  date        DATE NOT NULL
);
There is no foreign key, so nothing stops you

Delete a customer who has invoices and Postgres will not complain. The invoices survive, pointing at an id that no longer exists. Then the two halves of your dashboard start disagreeing:

  • fetchFilteredInvoices uses JOIN customers — an inner join, so orphaned invoices vanish from the invoices list.
  • fetchCardData runs SELECT COUNT(*) FROM invoices with no join — so the "Total Invoices" card still counts them.

No crash, no log line, just two numbers that quietly stop matching. You can confirm it against your own database in one query:

psqldiagnostic
SELECT invoices.id, invoices.customer_id
FROM invoices
LEFT JOIN customers ON invoices.customer_id = customers.id
WHERE customers.id IS NULL;

Two honest fixes. The database-level one is to declare the relationship you meant — customer_id UUID NOT NULL REFERENCES customers(id) ON DELETE CASCADE — correct, but a schema migration against a seeded database, and CREATE TABLE IF NOT EXISTS won't apply it to a table that already exists.

The application-level one fits this chapter: refuse.

app/lib/actions.tsedit
export async function deleteCustomer(id: string): Promise<CustomerState> {
  try {
    // invoices.customer_id has no foreign key, so deleting a customer with
    // invoices would orphan them: gone from the invoices list (inner join)
    // but still counted on the dashboard card (no join). Refuse instead.
    const [{ count }] = await sql<{ count: string }[]>`
      SELECT COUNT(*) FROM invoices WHERE customer_id = ${id}
    `;

    if (Number(count) > 0) {
      return {
        message: `Cannot delete: this customer still has ${count} invoice(s).`,
      };
    }

    await sql`DELETE FROM customers WHERE id = ${id}`;
  } catch (error) {
    console.error("Database Error:", error);
    return { message: "Database Error: Failed to Delete Customer." };
  }

  revalidatePath("/dashboard/customers");
  return { message: null };
}
The course's own delete button swallows this

DeleteInvoice wires up useActionState and then never renders state.message. Every database error it returns goes straight to the floor — the button just does nothing and the user has no idea why. Copy the structure and you inherit the silence, which is worse here, because a refusal is a message the user specifically needs to read.

whitespace-normal is not decoration

The cell this button sits in is whitespace-nowrap, inherited by the message. Without the override, a one-sentence refusal stretches the table sideways instead of wrapping inside its cell.

Finally the actions column: a sixth <th> with an sr-only label, a matching <td> holding <UpdateCustomer> and <DeleteCustomer>, the same pair in the mobile card — and a sixth cell in CustomersRowSkeleton, which is the one everybody forgets.

Checkpoint

Deleting a customer with invoices shows the refusal inline and leaves the row alone. A customer with no invoices deletes without a reload. Then check the dashboard: the customer count dropped, the invoice count didn't move — and the diagnostic query above still returns zero rows.

Known gaps

What this chapter deliberately leaves open, so the next person reading the repo doesn't mistake them for finished work:

  • No UNIQUE on customers.email — two customers can share an address. Schema-level, same as the missing foreign key, and out of scope until there's a migration story.
  • No pictures beyond the seeded six. Real uploads mean blob storage and a signed-upload endpoint; that's its own chapter, not a footnote in this one.
  • Icon-only edit links have no accessible name. The trash button has sr-only text; the pencil doesn't — in both the customers and invoices versions. One line each, worth doing in an accessibility pass rather than piecemeal.
  • Deleting is refused, not cascaded. A customer with invoices can't be removed at all. That's the safe default, not the right long-term answer.
