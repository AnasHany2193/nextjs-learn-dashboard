STEP 01Wire the customers page

app/dashboard/customers/page.tsx

Start with the smallest thing that works. The table takes a customers prop, and fetchFilteredCustomers already returns exactly that shape — currency formatted, sorted by name.

app/dashboard/customers/page.tsxedit
import { Metadata } from "next";
import { fetchFilteredCustomers } from "@/app/lib/data";

export const metadata: Metadata = {
  title: "Customers",

export default async function Page(props: {
  searchParams?: Promise<{ query?: string }>;
}) {
  const searchParams = await props.searchParams;
  const query = searchParams?.query || "";

  const customers = await fetchFilteredCustomers(query);

  return <CustomersTable customers={customers} />;

STEP 02Make search stream, not block

app/dashboard/customers/page.tsx app/ui/customers/table.tsx app/ui/skeletons.tsx

Right now the page awaits the query before rendering anything. Every keystroke blanks the screen until Postgres answers — the exact waterfall the invoices chapter taught you to break with <Suspense>.

So wrap the table in a boundary. Except the table looks like this:

app/ui/customers/table.tsxcurrent
<div className="w-full">
  <h1>Customers</h1>
  <Search placeholder="Search customers..." />   ← inside the table
  <div className="mt-6 flow-root">
    …rows…
This is the trap

The search input lives inside the component you're about to suspend. Wrap this in <Suspense> and every keystroke swaps the whole subtree — input included — for the fallback. React unmounts the real input, so the field loses focus and your cursor after one character. It looks like a debounce bug. It isn't.

The fix is structural: anything that must survive the reload goes outside the boundary. Hoist the heading and the search box into the page, and give the table the query so it can fetch its own data — the same shape app/dashboard/invoices/page.tsx already uses.

app/dashboard/customers/page.tsxedit
import { Suspense } from "react";
import { Metadata } from "next";

import Search from "@/app/ui/search";
import { lusitana } from "@/app/ui/fonts";
import { CustomersTableSkeleton } from "@/app/ui/skeletons";
import CustomersTable from "@/app/ui/customers/table";

export const metadata: Metadata = {
  title: "Customers",
};

export default async function Page(props: {
  searchParams?: Promise<{ query?: string }>;
}) {
  const searchParams = await props.searchParams;
  const query = searchParams?.query || "";

  return (
    <div className="w-full">
      <div className="flex w-full items-center justify-between">
        <h1 className={`${lusitana.className} text-2xl`}>Customers</h1>
      </div>

      <div className="mt-4 flex items-center justify-between gap-2 md:mt-8">
        <Search placeholder="Search customers..." />
      </div>

      {/* key remounts the boundary so the skeleton shows on every new query */}
      <Suspense key={query} fallback={<CustomersTableSkeleton />}>
        <CustomersTable query={query} />
      </Suspense>
    </div>
  );
}

The table now owns its fetch. Its signature changes from a prop to a query, and the three things you hoisted come out of its JSX.

Drop one wrapper

The table's outer <div className="w-full"> and its <div className="mt-6 flow-root"> are now redundant with each other — the page provides the outer one. Return the flow-root div directly and delete the rest of the nesting you no longer need.

STEP 03Show the demo login

+   <p className="mt-1">
+     user@nextmail.com &middot; 123456
+   </p>

Say why this is fine, because usually it isn't

Publishing a working password on a login screen is normally indefensible. It's fine here for reasons that are worth being able to state: the account is seeded from placeholder-data.ts, the database holds invented invoices for six invented customers, and the credentials are already public in this repo. Surfacing them changes nothing about the risk and makes the demo usable.

None of that survives contact with a real app. The moment there's a real user in that table, this block comes out.

Checkpoint

Open the deployed /login in a private window. You can sign in using only what's on the screen.

STEP 04Pagination — and why not yet

The invoices page paginates. The customers page doesn't, and the instinct is to make them match. Read the seed data first:

observed
customers seeded    6
invoices seeded    13
ITEMS_PER_PAGE      6   // app/lib/data.ts:90

Six customers at six per page is exactly one page. You would write a fetchCustomersPages query, add LIMIT/OFFSET, wire a <Pagination> component, and have no way to click page 2 — no way to tell working code from broken code.

The real prerequisite is data

If you want this, seed more customers first, then add pagination and actually verify it. Doing it in that order is the whole lesson. Doing it in the other order is how untested code gets shipped feeling tested.

When you do come back to it, it mirrors fetchInvoicesPages exactly — a COUNT(*) over the same ILIKE filter, divided by ITEMS_PER_PAGE, plus LIMIT/OFFSET on fetchFilteredCustomers and key={query + currentPage} on the Suspense boundary.
