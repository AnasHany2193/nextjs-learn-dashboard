Self-directed · Chapter 17 · Built

Bilingual routing and Arabic RTL

The Acme dashboard now serves /en and /ar with real Arabic slugs, a mirrored layout, and translated copy throughout. This is the record of building it — including the two authentication bypasses that only showed up because the routes were tested live, not read.

What shipped

  • Locale routing with next-intl 4.14.1 on Next 16.3.3
  • 15 route files moved under app/[locale]/, 2 route handlers deliberately left out
  • Two proxies — locale detection and auth — composed into one proxy.ts
  • 82 message keys per locale, verified at exact en/ar parity
  • Zero physical-direction Tailwind utilities left in the tree
  • Real Arabic URL slugs: /ar/الفواتير, not /ar/dashboard/invoices
  • Two auth bypasses found, fixed, and verified against a running server

Decisions, and how they held up

next-intl, not hand-rolled

Held up. The App Router has no built-in i18n routing — the i18n key in next.config is Pages Router only. Installed 4.14.1, which declares next: "… || ^16.0.0" and react: "… || ^19.0.0".

The naming mismatch is real

Next 16 renamed the file to proxy.ts, but next-intl has no next-intl/proxy entrypoint. You import createMiddleware from next-intl/middleware — inside a file called proxy.ts. Correct, not a bug.

Always prefix the locale

Held up, and step 09 leaned on it harder than expected. With localePrefix: "always" the locale segment is unambiguous, which is what lets the auth check read the locale off the raw pathname before next-intl has rewritten anything.

Arabic is a real locale, not English in a mirror

This one turned out to be the through-line of the whole chapter. Mirroring the layout was the easy half and took one mechanical pass. The other half — fonts without Arabic glyphs, a currency formatter pinned to en-US, plural forms, and eventually the URLs themselves — is where the real work was.

Same markup, opposite dir

Nothing in that right-hand panel has per-element RTL CSS. The dot, the label and the amount reverse because the layout uses gap and margin-inline-start rather than margin-left. That is the whole trick of step 06.

STEP 02Move every page under [locale]

The destructive step, and the reason this chapter runs before Cache Components. Fifteen route files moved with git mv; two stayed.

The route handlers do not move

app/query/route.ts and app/seed/route.ts are machine endpoints. There is no /ar version of a seed script. They stay at the root, need no layout, and get excluded from the proxy matcher in step 03. Same for app/ui/ and app/lib/, which were never routes.

The layout is where lang and dir get set — the two attributes the entire RTL story hangs off:

setRequestLocale(locale);   // opts this subtree back into static rendering

const dir = locale === "ar" ? "rtl" : "ltr";

return (

    <body className={`${bodyFont(locale).className} antialiased`}>
      <NextIntlClientProvider>{children}</NextIntlClientProvider>
    </body>
  </html>
);

STEP 03Compose the proxy — and the first bypass

proxy.ts auth.config.ts

Two systems want the same slot. The obvious composition is the one next-intl's own docs show, and it is what this chapter originally planned:

proxy.tsthe trap
const handleLocale = createMiddleware(routing);
const { auth } = NextAuth(authConfig);

export default auth((req) => handleLocale(req));
This compiles, runs, and silently disables authentication

authConfig.callbacks.authorized() is only auto-enforced by the bare export default auth form. The moment you wrap auth() around your own function — which is required to run next-intl alongside it — the framework stops acting on that callback's verdict. It still calls it. It just ignores what comes back.

Result: every dashboard route was reachable while logged out, in both locales. No error, no warning, no log line. The page just renders.

This was not found by reading the code. It was found by requesting the route and being surprised, then instrumenting the callback to see what it actually computed:

observeddiagnostic
[authorized debug] {
  pathname: '/ar/dashboard/customers',
  path: '/dashboard/customers',
  isOnDashboard: true,
  isLoggedIn: false          ← returns false, page serves 200 anyway
}

The callback was right. Nothing was listening. The fix is to stop relying on the framework to enforce it and check req.auth yourself, inside the composed function:

proxy.tsfix
export default auth((req) => {
  const isLoggedIn = !!req.auth?.user;
  const locale = localeOf(req.nextUrl.pathname);
  const path = stripLocale(req.nextUrl.pathname);
  const dashboardPath = localizedPath("/dashboard", locale);
  const loginPath = localizedPath("/login", locale);

  if (path.startsWith(dashboardPath) && !isLoggedIn) {
    return NextResponse.redirect(new URL(`/${locale}${loginPath}`, req.nextUrl));
  }

  if (path === loginPath && isLoggedIn) {
    return NextResponse.redirect(
      new URL(`/${locale}${dashboardPath}`, req.nextUrl),
    );
  }

  return handleLocale(req);
});
Leave the dead callback, but label it

authorized() stays in auth.config.ts because NextAuthConfig expects the shape. It carries a comment saying it is not on the request path, so the next person doesn't read it and assume it's protecting anything.

The matcher also changes twice: query and seed get excluded so the unprefixed route handlers aren't locale-redirected, and .*\\.png$ widens to .*\\..* so every static asset is skipped rather than just PNGs.

Verified

Logged out, /ar/dashboard/customers → 307 → the Arabic login. /en/dashboard → 307 → /en/login. /seed and /query still 200. Checked against a running server, not inferred.

STEP 04Make every navigation locale-aware

Mechanically an import swap, repeated across 16 files:

every file that links internallyedit
- import Link from "next/link";
+ import { Link } from "@/i18n/navigation";

Exactly one next/link import survives, in app/[locale]/page.tsx, for the external nextjs.org/learn link. It's aliased to NextLink so the difference is visible at the call site rather than hidden in the import block.

Two components needed no logic change at all

pagination.tsx and search.tsx build URLs from usePathname() plus URLSearchParams rather than hardcoding paths. Swapping the import was enough. That is what "don't hardcode routes" buys you, two chapters later.

Server actions needed real changes: four redirect calls and six revalidatePath calls, split across invoices and customers.

app/lib/actions.tsedit
- revalidatePath("/dashboard/customers");
- redirect("/dashboard/customers");
+ revalidatePath("/[locale]/dashboard/customers", "page");
+ redirect({ href: "/dashboard/customers", locale: await getLocale() });
The delete actions are the ones to double-check

deleteInvoice and deleteCustomer revalidate but never redirect — they run from a button inside a table, not a form page. They still need the locale-aware revalidatePath, or deleting in Arabic quietly refreshes the English list and leaves the Arabic one stale.

STEP 05Extract the copy

The step that looked like the tedious one and turned out to be the one that was silently unfinished for longest. Message files existed and had content. Nothing read them.

Having messages is not the same as using them

You can complete steps 01 through 04, load /ar, see a correctly mirrored RTL layout with an Arabic font — and every single label still in English. The layout work and the copy work are independent, and the layout work is the one that looks like progress.

The check that catches it: grep the tree for JSX text nodes that aren't a t() call. It should return nothing.

terminal
grep -rE ">[A-Z][a-z]+( [A-Za-z]+){0,4}<" app/ui app/\[locale\] --include=*.tsx \
  | grep -vE "t\(|\{|>Acme<"

Namespaces landed as Meta, Nav, Home, Login, Dashboard, Customers, Invoices — 82 keys each side, verified identical between en.json and ar.json by script rather than by eye.

One string genuinely needs ICU plurals

The delete refusal, "still has {count} invoice(s)", is the English shrug. Arabic has six plural categories and "(s)" maps to none of them:

messages/ar.jsonedit
"cannotDelete": "{count, plural, =0 {لا توجد فواتير} one {…فاتورة واحدة}
  two {…فاتورتان} few {# فواتير} many {# فاتورة} other {# فاتورة}}"
Data is not copy

The avatar picker derives its option labels from filenames — "amy burns", "lee robinson". Those are people's names. They stay identical in both locales, as do the seeded customer names in the table. Only "No picture (use initials)" and the listbox's aria-label belong in messages/.

STEP 06Direction and RTL styles

One mechanical pass over 18 files, ~80 utilities. Find them with:

Tailwind 3.4.17 emits padding-inline-start, margin-inline-start, inset-inline-start and border-inline-start-width, and registers the variant as &:where([dir="rtl"], [dir="rtl"] *). No plugin, no config change.

It emits physical margin-left. Where the parent was already a flex container, gap-* replaced it outright — direction-agnostic by construction. The one case that couldn't be replaced is pagination's -space-x-px, which exists to collapse adjacent borders; gap can't reproduce a negative overlap, so that one keeps rtl:space-x-reverse.

Five rtl: overrides survive in the whole tree, and all five are deliberate: the pagination chevrons, the login button arrow, and the homepage arrow get rtl:rotate-180, because logical properties move an icon but never flip it. Nothing else is rotated. A mirrored trash can is the classic over-correction.

STEP 07Numbers, dates and money

Three formatters were pinned to en-US, and chapter 16 had widened the blast radius — formatCurrency now runs on the customers table's totals as well as every invoice.

The decision this step actually turned on

fetchFilteredCustomers formats currency inside the data layer, before any component sees it. So either the locale threads down into the fetch, or formatting moves out of data.ts into the components.

What shipped: getLocale() called inside data.ts itself. It works because these functions only ever run inside a request scope, and it avoided a refactor of both tables. The cleaner long-term shape is still moving presentation out of the data layer — a data layer shouldn't be deciding how money looks. Recorded here as a deliberate trade, not an oversight.

A real decision, not a formatting detail

Arabic has two numeral systems. ar defaults to Arabic-Indic digits (٠١٢٣), but plenty of Gulf and Levantine business UIs use Western digits. If you want Western digits in an Arabic UI that's ar-u-nu-latn — an actual Unicode extension, not a hack. Pick one deliberately and write down why.

STEP 08Metadata and the switcher

generateMetadata now reads from a Meta namespace and sets openGraph.locale per locale. The switcher preserves path, dynamic segments and search params:

app/ui/locale-switcher.tsxnew
const pathname = usePathname();      // locale-free
const params = useParams();          // keeps [id] segments
const searchParams = useSearchParams();

function switchTo(nextLocale: string) {
  const query = Object.fromEntries(searchParams.entries());
  router.replace({ pathname, params, query }, { locale: nextLocale });
}
The hreflang half is still wrong — see Known gaps

The alternates.languages block lives in the root layout, which knows the locale but not which page matched. So every page emits the same alternates, pointing at the site root. Getting this right means moving alternates into each page's own generateMetadata.

STEP 09Real Arabic route slugs

i18n/routing.ts app/ui/breadcrumbs.tsx app/ui/pagination.tsx app/ui/customers/buttons.tsx app/ui/invoices/buttons.tsx

This step was not in the original plan. Translating the labels but leaving /ar/dashboard/invoices in the address bar is a half-measure — the URL is copy too.

i18n/routing.tsedit
pathnames: {
  "/": "/",
  "/login": { en: "/login", ar: "/تسجيل-الدخول" },
  "/dashboard": { en: "/dashboard", ar: "/لوحة-التحكم" },
  "/dashboard/invoices": {
    en: "/dashboard/invoices",
    ar: "/لوحة-التحكم/الفواتير",
  },
  "/dashboard/invoices/[id]/edit": {
    en: "/dashboard/invoices/[id]/edit",
    ar: "/لوحة-التحكم/الفواتير/[id]/تعديل",
  },
  // …9 entries total
}

Two things make this cheaper than it sounds. The filesystem doesn't change — the proxy rewrites the Arabic URL to the internal path before Next's router sees it. And every Link already goes through @/i18n/navigation, so the calling code keeps using the internal key and gets the right slug for free.

Typed pathnames break interpolated hrefs — on purpose

Once pathnames is defined, Link's href stops accepting arbitrary strings. Four call sites broke at compile time, which is the tooling doing its job:

app/ui/customers/buttons.tsxedit
- href={`/dashboard/customers/${id}/edit`}
+ href={{ pathname: "/dashboard/customers/[id]/edit", params: { id } }}

Pagination needed the same treatment for a different reason — it was concatenating ?page=… onto the pathname as a raw string, which no longer satisfies the type. It now passes { pathname, query } separately. breadcrumbs.tsx, being generic, types its href as React.ComponentProps<typeof Link>["href"] so it inherits whatever Link accepts instead of duplicating the union.

The second bypass

Build passed. Types passed. Then the Arabic dashboard URL was requested logged out and returned 200 with real content.

observeddiagnostic
[proxy debug] {
  raw:           '/ar/%D9%84%D9%88%D8%AD%D8%A9-%D8%A7%D9%84%D8%AA%D8%AD%D9%83%D9%85',

req.nextUrl.pathname is percent-encoded and never auto-decodes

At the middleware level the pathname is raw. The browser address bar shows you /ar/لوحة-التحكم; your code receives /ar/%D9%84%D9%88…. routing.pathnames holds literal Unicode, so startsWith compared encoded against decoded and silently returned false — and the auth check no-opped for the second time in one chapter, via a completely different mechanism.

auth.config.tsfix
function stripLocale(pathname: string) {
  const decoded = decodeURIComponent(pathname);   // once, here
  const segments = decoded.split("/");
  …
}

Decoding inside the two shared helpers fixes it for both proxy.ts and auth.config.ts at once — every caller is correct by construction rather than by remembering.

Verified

/ar/لوحة-التحكم logged out → 307 → /ar/تسجيل-الدخول. Nested slugs too. /ar/login (the English word) → 307 → the real Arabic slug, handled by next-intl itself with no code of ours.

What the plan got wrong

This chapter existed as a written plan before any of it was built. Three things the plan did not survive contact with:

The plan saidWhat actually happened
"Verify the sign-in redirect yourself — the locale might get dropped." Far worse. The locale wasn't dropped; the entire auth check wasn't running. The plan anticipated a cosmetic redirect bug and missed a total bypass.
Step 05 framed as "the tedious part" — mechanical extraction. Tedious, yes, but also the step most likely to look done while being untouched. Mirrored layout plus Arabic font plus English labels reads as progress.
No mention of localized URL slugs at all. Became step 09, and dragged a second auth bypass in with it. A plan that stops at translated labels stops one step short of the actual feature.
The pattern worth keeping

Both bypasses passed pnpm build, passed tsc, and looked correct in review. Both were found the same way: request the route, be surprised by the response, then instrument the code and read what it actually computed. Neither would have been caught by reading harder.

Known gaps

  • hreflang alternates are wrong on every page. alternates.languages is hardcoded to /en and /ar in the root layout, which can't know which page matched. Verified still broken. Fixing it means per-page generateMetadata using getPathname — nine files.
  • Presentation still lives in the data layer. getLocale() inside data.ts works, but formatting money is a component's job.
  • pages.signIn is a bare "/login". It's static config, so it can't be locale-aware. It's off the enforced path now, but it would be wrong if anything started relying on it.
  • The pathnames map is a second list to maintain. Add a route and forget the entry, and /ar 404s silently.

Commits

Two, deliberately split so the security work is reviewable on its own rather than buried in a 45-file feature diff:

fix(auth): enforce dashboard protection under locale routing
feat(i18n): add english/arabic locale routing with rtl and localized slugs
Why not five commits

Because none of this was committed incrementally, every UI file's RTL pass, translation wiring and typed-href fix are flattened into one diff. Splitting further would mean reconstructing intermediate file states to fake a history that never existed. The auth layer is cleanly separable — so that's where the line got drawn.

What this chapter isn't

The SEO half is still a rehearsal

Step 08 emits alternates and a canonical. Step 09 produces genuinely well-formed localized URLs. No crawler will ever see any of it — everything meaningful sits behind authorized(), which this chapter spent most of its effort making actually work. The entire i18n SEO surface is unreachable to Googlebot by design.

That doesn't make it wasted, but it does make it practice, not portfolio. /ar routing on a login-walled dashboard is not a line on a CV, and it does not move the Phase 2 number.

What it did produce is harder to put on a CV and worth more: two authentication bypasses, in a framework composition that every tutorial demonstrates, found only because the running app was tested rather than the code re-read. The second one — percent-encoded pathnames never matching Unicode slugs — is the kind of bug that ships to production in a real Arabic app and survives code review indefinitely, because the code looks obviously correct.
