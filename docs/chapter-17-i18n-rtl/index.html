Bilingual routing and Arabic RTL

Take the Acme dashboard from one hardcoded English tree to /en and /ar routes with a properly mirrored layout — and find every place the course quietly assumed left-to-right.

In this chapter

  • Add locale routing with next-intl, verified against your installed Next 16.3.3
  • Move every page under an app/[locale]/ segment without breaking the route handlers
  • Compose two proxies — locale detection and auth — into one proxy.ts
  • Replace ~55 physical-direction Tailwind utilities across 17 files with logical ones
  • Fix the currency, date and numeral formatting the course hardcoded to en-US
  • Emit hreflang alternates, and understand why they do nothing for this app

Decisions, made up front

Three choices shape everything downstream. Here they are with the reasoning, so you can disagree before you write code rather than halfway through step 4.

next-intl, not hand-rolled

The App Router has no built-in i18n routing — the i18n key in next.config is Pages Router only. "Built-in" really means hand-writing locale detection, a message loader, and a Link wrapper. That teaches you the mechanism, but you'd be rebuilding a solved problem, and your day job is an Arabic Next.js site where knowing the library people actually use is worth more.

Verified

next-intl 4.14.0 declares next: "… || ^16.0.0" and react: "… || ^19.0.0" in its peer dependencies, so it's compatible with your 16.3.3 / 19.2.8. Its published entrypoints include /routing, /navigation, /middleware, /server, /plugin and /config.

Naming gotcha

Next 16 renamed the file to proxy.ts, but next-intl has no next-intl/proxy entrypoint. You still import createMiddleware from next-intl/middleware — inside a file called proxy.ts. That mismatch is correct, not a bug.

Always prefix the locale

Three options: always (/en/dashboard, /ar/dashboard), as-needed (/dashboard for English, /ar/dashboard for Arabic), or never.

Go with always. In an app where neither language is really "the default", as-needed makes English an invisible privileged case, and every debugging session starts with "wait, which locale am I on?" It also means one hreflang pattern instead of two, and no bare-path canonical ambiguity. The cost is that /dashboard now redirects rather than resolves — which is exactly the honest thing for it to do.

Arabic is a real locale, not English in a mirror

Mirroring the layout is the easy half. The half that bites: your fonts are latin-subset only, your currency formatter is pinned to en-US, and generateYAxis builds labels by string-concatenating a $. Step 5 deals with all three.

What "mirrored" means — same markup, opposite dir

Don't localise the route handlers

app/query/route.ts and app/seed/route.ts are machine endpoints, not pages. There is no /ar version of a seed script. Leave them at the root — they need no layout, so they're unaffected by the move. Same for app/ui/ and app/lib/, which aren't routes at all.

Now the layout carries the locale. This is where lang and dir get set — the two attributes the entire RTL story hangs off.

app/[locale]/layout.tsxedit
import "@/app/ui/global.css";
import { notFound } from "next/navigation";
import { hasLocale, NextIntlClientProvider } from "next-intl";
import { setRequestLocale } from "next-intl/server";
import { routing } from "@/i18n/routing";
import { bodyFont } from "@/app/ui/fonts";

export function generateStaticParams() {
  return routing.locales.map((locale) => ({ locale }));
}

export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: Promise<{ locale: string }>;
}) {
  const { locale } = await params;
  if (!hasLocale(routing.locales, locale)) notFound();

  // opts this subtree back into static rendering
  setRequestLocale(locale);

  const dir = locale === "ar" ? "rtl" : "ltr";

  return (
    <html lang={locale} dir={dir}>
      <body className={`${bodyFont(locale).className} antialiased`}>
        <NextIntlClientProvider>{children}</NextIntlClientProvider>
      </body>
    </html>
  );
}

Second, with no root app/layout.tsx, a request that matches no locale has no layout to render its 404 in. Confirm how your Next 16 build handles that — app/global-not-found.tsx is the current answer — before you decide you're done with this step.

STEP 03Compose the proxy: locale + auth

proxy.ts auth.config.ts

Right now proxy.ts is one line: NextAuth(authConfig).auth. Two systems now want that slot. Auth runs outside, locale routing runs inside — so an unauthenticated request gets redirected to login with its locale intact.

proxy.tsedit
import NextAuth from "next-auth";
import createMiddleware from "next-intl/middleware";

import { routing } from "./i18n/routing";
import { authConfig } from "./auth.config";

const handleLocale = createMiddleware(routing);
const { auth } = NextAuth(authConfig);

export default auth((req) => handleLocale(req));

export const config = {
  matcher: ["/((?!api|_next/static|_next/image|query|seed|.*\\..*).*)"],
};
The matcher changed twice

query and seed are now excluded — they're unprefixed route handlers and must not be locale-redirected. And .*\\.png$ widened to .*\\..* so every static asset is skipped, not just PNGs.

Now authorized() is comparing against paths that no longer exist. /ar/dashboard does not start with /dashboard, so every Arabic dashboard route is currently unprotected. Strip the locale before you test.

auth.config.tsedit
import type { NextAuthConfig } from "next-auth";
import { routing } from "./i18n/routing";

// "/ar/dashboard/invoices" -> "/dashboard/invoices"
function stripLocale(pathname: string) {
  const segments = pathname.split("/");
  const maybeLocale = segments[1] as (typeof routing.locales)[number];
  if (routing.locales.includes(maybeLocale)) {
    return "/" + segments.slice(2).join("/");
  }
  return pathname;
}

function localeOf(pathname: string) {
  const maybeLocale = pathname.split("/")[1] as (typeof routing.locales)[number];
  return routing.locales.includes(maybeLocale)
    ? maybeLocale
    : routing.defaultLocale;
}

export const authConfig = {
  pages: {
    signIn: "/login", // next-intl re-prefixes this
  },
  callbacks: {
    authorized({ auth, request: { nextUrl } }) {
      const isLoggedIn = !!auth?.user;
      const locale = localeOf(nextUrl.pathname);
      const path = stripLocale(nextUrl.pathname);
      const isOnDashboard = path.startsWith("/dashboard");

      if (isOnDashboard) return isLoggedIn;
      if (isLoggedIn) {
        return Response.redirect(new URL(`/${locale}/dashboard`, nextUrl));
      }
      return true;
    },
  },
  providers: [],
} satisfies NextAuthConfig;
Verify the sign-in redirect yourself

pages.signIn is a bare /login and next-auth doesn't know about locales. Whether the locale survives the redirect depends on whether next-auth's redirect lands before or after next-intl's rewrite. Test both /ar/dashboard and /en/dashboard logged out. If an Arabic user gets dropped on the English login page, handle the prefixing here rather than fighting it later.

Checkpoint

Logged out, /ar/dashboard redirects to an Arabic login. Logged in, /ar/login bounces to /ar/dashboard, not /en/dashboard. Bare /dashboard redirects to /en/dashboard. /seed still responds.

The active-link check

nav-links.tsx compares pathname === link.href. Under a locale prefix, usePathname() from next/navigation returns /en/dashboard and the comparison never matches, so the active state silently dies. next-intl's usePathname strips the prefix, which makes the existing comparison correct again — one import change, no logic change.

Server actions

actions.ts has two redirect("/dashboard/invoices") calls and three revalidatePath calls. The redirects need the locale-aware version; the revalidations need to cover both locales, since /en/dashboard/invoices and /ar/dashboard/invoices are separate cache entries.

app/lib/actions.tsedit
- import { redirect } from "next/navigation";
+ import { redirect } from "@/i18n/navigation";
+ import { getLocale } from "next-intl/server";

// inside createInvoice / updateInvoice:
- revalidatePath("/dashboard/invoices");
- redirect("/dashboard/invoices");
+ revalidatePath("/[locale]/dashboard/invoices", "page");
+ redirect({ href: "/dashboard/invoices", locale: await getLocale() });
Confirm the revalidate shape

Passing a dynamic route pattern plus "page" is how you invalidate every locale in one call, but it's the kind of API that shifts between versions. If it doesn't take, fall back to an explicit loop over routing.locales — less elegant, obviously correct.

Also update sidenav.tsx: signOut({ redirectTo: "/" }) drops the user into the default locale. Read the current locale and send them to /${locale}.

Checkpoint

STEP 05Direction, type, and numbers

The dir attribute from step 2 is already doing work. What's left is the CSS that ignores it.

Physical → logical utilities

Your app has roughly 55 direction-bound utilities across 17 files. Every one of them is a place the Arabic layout breaks. Find them with:

terminal
grep -rnE "(pl-|pr-|ml-|mr-|left-|right-|text-left|text-right|rounded-l-|rounded-r-|border-l-|border-r-|space-x-)" \
  app --include="*.tsx" --include="*.css"
Verified

Tailwind 3.4.17 — your installed version — ships all of these. Its core plugins emit padding-inline-start, margin-inline-start, inset-inline-start and border-inline-start-width, and it registers the variants as &:where([dir="rtl"], [dir="rtl"] *). No plugin, no config change.

space-x is the one that fools you

space-x-* emits physical margin-left and has no logical equivalent. Tailwind's official fix is to add rtl:space-x-reverse, but the better fix is to delete it: the parents are already flex containers, so gap-2 does the same job and is direction-agnostic by construction. You have three of these — space-x-2, space-x-1, md:space-x-0 — all in sidenav.tsx and breadcrumbs.tsx.

Icons that point somewhere — the pagination chevrons — are a separate problem. Logical properties move them; nothing flips them. Add rtl:rotate-180 to the arrow icons, and to nothing else. A rotated user avatar is the classic over-mirroring bug.

Fonts

fonts.ts loads Inter and Lusitana with subsets: ["latin"]. Neither contains a single Arabic glyph, so /ar renders in whatever the OS falls back to — different on your machine than on your reviewer's.

app/ui/fonts.tsedit
import { Inter, Lusitana, IBM_Plex_Sans_Arabic } from "next/font/google";

export const inter = Inter({ subsets: ["latin"] });
export const lusitana = Lusitana({ weight: ["400", "700"], subsets: ["latin"] });

export const plexArabic = IBM_Plex_Sans_Arabic({
  weight: ["400", "500", "600"],
  subsets: ["arabic"],
});

// used by app/[locale]/layout.tsx
export const bodyFont = (locale: string) =>
  locale === "ar" ? plexArabic : inter;

Lusitana is a display serif with no Arabic counterpart at all. Wherever it's used for headings, either fall back to the Arabic body face in /ar or pick a deliberate Arabic display face — don't let it silently degrade.

A real decision, not a formatting detail

Arabic has two numeral systems. ar defaults to Arabic-Indic digits (٠١٢٣), ar-EG too, but many Gulf and Levantine business UIs use Western digits. If you want Western digits in an Arabic UI, that's the ar-u-nu-latn locale tag — not a hack, an actual Unicode extension. Pick one deliberately and write down why; this is exactly the question your day job will ask you.

What this chapter isn't

The hreflang work is a rehearsal

Step 6 emits correct alternates and a correct canonical. No crawler will ever see them. Everything meaningful in this app sits behind authorized(), so the entire i18n SEO surface — hreflang, localised metadata, per-locale canonicals — is unreachable to Googlebot. You are learning the mechanism on a page nobody will index.

That's a fine reason to do it, as long as it stays labelled. It does not move your Phase 2 deliverable, and /ar routing on a login-walled dashboard is not a line on your CV. The value here is that when you build the public project that does carry the LCP number, bilingual routing will be a solved problem you've already debugged once — including the two parts that always break, which are proxy composition and the auth path check.

The part that pays immediately is different and worth naming: your day job is an Arabic Next.js site. Steps 3 and 5 are the two places production bilingual apps actually break, and you'll have hit both here first, with nothing at stake.
