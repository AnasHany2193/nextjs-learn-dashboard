Self-directed · Chapter 17

Bilingual routing and Arabic RTL

Take the Acme dashboard from one hardcoded English tree to /en and /ar routes with a properly mirrored layout — and find every place the course, and chapter 16, quietly assumed left-to-right.

In this chapter

  • Add locale routing with next-intl, verified against your installed Next 16.3.3
  • Move fifteen route files under app/[locale]/ without breaking the two route handlers
  • Compose two proxies — locale detection and auth — into one proxy.ts
  • Convert eleven next/link imports and ten server-action redirects to locale-aware equivalents
  • Replace ~80 physical-direction Tailwind utilities across 18 files with logical ones
  • Fix the currency, date and numeral formatting hardcoded to en-US
  • Emit hreflang alternates, and understand why they do nothing for this app

Decisions, made up front

Three choices shape everything downstream. Here they are with the reasoning, so you can disagree before you write code rather than halfway through step 4.

next-intl, not hand-rolled

The App Router has no built-in i18n routing — the i18n key in next.config is Pages Router only. "Built-in" really means hand-writing locale detection, a message loader, and a Link wrapper. That teaches you the mechanism, but you'd be rebuilding a solved problem, and your day job is an Arabic Next.js site where knowing the library people actually use is worth more.

Verified

next-intl 4.14.2 declares next: "… || ^16.0.0" and react: "… || ^19.0.0" in its peer dependencies, so it's compatible with your 16.3.3 / 19.2.8. Its published entrypoints include /routing, /navigation, /middleware, /server, /plugin and /config.

Naming gotcha

Next 16 renamed the file to proxy.ts, but next-intl has no next-intl/proxy entrypoint. You still import createMiddleware from next-intl/middleware — inside a file called proxy.ts. That mismatch is correct, not a bug.

Always prefix the locale

Three options: always (/en/dashboard, /ar/dashboard), as-needed (/dashboard for English, /ar/dashboard for Arabic), or never.

Go with always. In an app where neither language is really "the default", as-needed makes English an invisible privileged case, and every debugging session starts with "wait, which locale am I on?" It also means one hreflang pattern instead of two. The cost is that /dashboard now redirects rather than resolves — which is exactly the honest thing for it to do.

Arabic is a real locale, not English in a mirror

Mirroring the layout is the easy half. The half that bites: your fonts are latin-subset only, your currency formatter is pinned to en-US, and generateYAxis builds labels by string-concatenating a $. Steps 6 and 7 deal with all three.

Don't localise the route handlers

app/query/route.ts and app/seed/route.ts are machine endpoints, not pages. There is no /ar version of a seed script. Leave them at the root — they need no layout, so they're unaffected by the move. Same for app/ui/ and app/lib/, which aren't routes at all.

Now the layout carries the locale. This is where lang and dir get set — the two attributes the entire RTL story hangs off.

STEP 03Compose the proxy: locale + auth

proxy.ts auth.config.ts

Right now proxy.ts is one line: NextAuth(authConfig).auth. Two systems now want that slot. Auth runs outside, locale routing runs inside — so an unauthenticated request gets redirected to login with its locale intact.

proxy.tsedit
import NextAuth from "next-auth";
import createMiddleware from "next-intl/middleware";

import { routing } from "./i18n/routing";
import { authConfig } from "./auth.config";

const handleLocale = createMiddleware(routing);
const { auth } = NextAuth(authConfig);

export default auth((req) => handleLocale(req));

export const config = {
  matcher: ["/((?!api|_next/static|_next/image|query|seed|.*\\..*).*)"],
};
The matcher changed twice

query and seed are now excluded — they're unprefixed route handlers and must not be locale-redirected. And .*\\.png$ widened to .*\\..* so every static asset is skipped, not just PNGs. That second one matters more than it used to: the avatar picker loads six PNGs from public/customers/ on every form render.

Now authorized() is comparing against paths that no longer exist. /ar/dashboard does not start with /dashboard, so every Arabic dashboard route is currently unprotected. Strip the locale before you test.

auth.config.tsedit
import { routing } from "./i18n/routing";

// "/ar/dashboard/customers" -> "/dashboard/customers"
function stripLocale(pathname: string) {
  const segments = pathname.split("/");
  const maybeLocale = segments[1] as (typeof routing.locales)[number];
  if (routing.locales.includes(maybeLocale)) {
    return "/" + segments.slice(2).join("/");
  }
  return pathname;
}

function localeOf(pathname: string) {
  const maybeLocale = pathname.split("/")[1] as (typeof routing.locales)[number];
  return routing.locales.includes(maybeLocale)
    ? maybeLocale
    : routing.defaultLocale;
}

callbacks: {
  authorized({ auth, request: { nextUrl } }) {
    const isLoggedIn = !!auth?.user;
    const locale = localeOf(nextUrl.pathname);
    const path = stripLocale(nextUrl.pathname);
    const isOnDashboard = path.startsWith("/dashboard");

    if (isOnDashboard) return isLoggedIn;
    if (isLoggedIn) {
      return Response.redirect(new URL(`/${locale}/dashboard`, nextUrl));
    }
    return true;
  },
},
Verify the sign-in redirect yourself

pages.signIn is a bare /login and next-auth doesn't know about locales. Whether the locale survives the redirect depends on whether next-auth's redirect lands before or after next-intl's rewrite. Test both /ar/dashboard and /en/dashboard logged out. If an Arabic user gets dropped on the English login page, handle the prefixing here rather than fighting it later.

Checkpoint

Logged out, /ar/dashboard/customers redirects to an Arabic login. Logged in, /ar/login bounces to /ar/dashboard. Bare /dashboard redirects to /en/dashboard. /seed still responds, and customer avatars still load.

- import Link from "next/link";

Keep next/link in app/[locale]/page.tsx for the external nextjs.org/learn link — that one has no locale to carry.

The active-link check

nav-links.tsx compares pathname === link.href. Under a locale prefix, usePathname() from next/navigation returns /en/dashboard and the comparison never matches, so the active state silently dies. next-intl's usePathname strips the prefix, which makes the existing comparison correct again — one import change, no logic change.

Two already fine

pagination.tsx and search.tsx build URLs from usePathname() + URLSearchParams rather than hardcoding. Swap their imports for consistency, but the logic needs no change — they were always deriving the path. This is what "don't hardcode routes" buys you, two chapters later.

Server actions

actions.ts now has four redirect calls and six revalidatePath calls, split across invoices and customers. The redirects need the locale-aware version; the revalidations need to cover both locales, since /en/dashboard/customers and /ar/dashboard/customers are separate cache entries.

app/lib/actions.tsedit
- import { redirect } from "next/navigation";
+ import { redirect } from "@/i18n/navigation";
+ import { getLocale } from "next-intl/server";

// x2 in the invoice actions, x2 in the customer actions:
- revalidatePath("/dashboard/customers");
- redirect("/dashboard/customers");
+ revalidatePath("/[locale]/dashboard/customers", "page");
+ redirect({ href: "/dashboard/customers", locale: await getLocale() });
deleteCustomer has no redirect, and that's the tricky one

deleteInvoice and deleteCustomer revalidate but return instead of redirecting — they run from a button inside the table, not a form page. They still need the locale-aware revalidatePath, or deleting in Arabic leaves the Arabic list stale while quietly refreshing the English one.

Confirm the dynamic-pattern shape works in your version. If revalidatePath("/[locale]/…", "page") doesn't take, fall back to an explicit loop over routing.locales — less elegant, obviously correct.

Also update sidenav.tsx: signOut({ redirectTo: "/" }) drops the user into the default locale. Read the current locale and send them to /${locale}. Same for the callbackUrl default in login-form.tsx, which is a bare "/dashboard".

Checkpoint

From /ar/dashboard/customers, every sidebar link, breadcrumb, pagination link, create/edit/cancel button and sign-out keeps you in /ar. The active nav highlight works again. Creating a customer returns you to the Arabic customers list. Deleting one updates the Arabic list, not the English one.

The refusal message is a plural, not a string

"still has {count} invoice(s)" is the English-shrug version. Arabic has six plural forms — zero, one, two, few, many, other — and "(s)" maps to none of them. next-intl uses ICU message syntax, so this is the one string in the app that genuinely needs it:

messages/ar.jsonedit
"cannotDelete": "{count, plural, =0 {لا توجد فواتير} one {لا يمكن الحذف: لدى هذا العميل فاتورة واحدة} two {لا يمكن الحذف: لدى هذا العميل فاتورتان} few {لا يمكن الحذف: لدى هذا العميل # فواتير} many {لا يمكن الحذف: لدى هذا العميل # فاتورة} other {لا يمكن الحذف: لدى هذا العميل # فاتورة}}"
Do not translate the avatar labels

AvatarPicker derives its option labels from filenames — "amy burns", "lee robinson", "delba de oliveira". Those are people's names, not UI copy. They stay as they are in both locales. The only strings in that component that belong in messages/ are "No picture (use initials)" and the listbox's aria-label.

The same rule catches the seeded customer names in the table. Data is not copy.

Server components use getTranslations; client components use useTranslations. The customers forms are "use client", so they take the hook; the table and the route pages are server components and take the async version.

Checkpoint

STEP 06Direction and RTL styles

18 files under app/ui/

The dir attribute from step 2 is already doing work. What's left is the CSS that ignores it — ~80 direction-bound utilities across 18 files. Find them with:

terminal
grep -rnE "(pl-|pr-|ml-|mr-|left-|right-|text-left|text-right|rounded-l-|rounded-r-|border-l-|border-r-|space-x-)" \

Verified

Tailwind 3.4.17 — your installed version — ships all the logical equivalents. Its core plugins emit padding-inline-start, margin-inline-start, inset-inline-start and border-inline-start-width, and it registers the variants as &:where([dir="rtl"], [dir="rtl"] *). No plugin, no config change.

space-x is the one that fools you

space-x-* emits physical margin-left and has no logical equivalent. Tailwind's official fix is rtl:space-x-reverse, but the better fix is to delete it: the parents are already flex containers, so gap-* does the same job and is direction-agnostic by construction.

Icons that point somewhere — the pagination chevrons, the login button's arrow — are a separate problem. Logical properties move them; nothing flips them. Add rtl:rotate-180 to those, and to nothing else. A rotated user avatar or a mirrored trash can is the classic over-mirroring bug.

One thing you already got right

AvatarPicker's dropdown panel is absolute … w-full with no left or right anchor, so it spans its relative parent and mirrors for free. Worth noticing why it survives: it was sized to its container instead of positioned against an edge. The field icons at left-3 are the opposite choice, and they're the ones you have to fix.

Fonts

fonts.ts loads Inter and Lusitana with subsets: ["latin"]. Neither contains a single Arabic glyph, so /ar renders in whatever the OS falls back to — different on your machine than on your reviewer's.

app/ui/fonts.tsedit
import { Inter, Lusitana, IBM_Plex_Sans_Arabic } from "next/font/google";

export const plexArabic = IBM_Plex_Sans_Arabic({
  weight: ["400", "500", "600"],
  subsets: ["arabic"],
});

// used by app/[locale]/layout.tsx
export const bodyFont = (locale: string) =>
  locale === "ar" ? plexArabic : inter;

Lusitana is a display serif with no Arabic counterpart at all. Wherever it's used for headings — and it's used in breadcrumbs.tsx, every page heading, and both forms — either fall back to the Arabic body face in /ar or pick a deliberate Arabic display face. Don't let it silently degrade.

Checkpoint

Load /ar/dashboard/customers and compare against /en side by side. Sidebar on the right, search icon on the correct edge of its input, chevrons pointing outward correctly, table columns right-to-left, avatar picker panel aligned to its field. Then re-check /en — logical properties should have changed nothing there.

These are called from server components, which don't take props from the URL

fetchFilteredCustomers formats currency inside the data layer, before any component sees it. So threading a locale through means either passing it down from the page into the fetch, or moving formatting out of data.ts and into the components that render it.

The second is the better shape — data layers shouldn't decide presentation — but it's a real refactor of both tables, not a one-line change. Decide which before you start.

A real decision, not a formatting detail

Arabic has two numeral systems. ar defaults to Arabic-Indic digits (٠١٢٣), but many Gulf and Levantine business UIs use Western digits. If you want Western digits in an Arabic UI, that's the ar-u-nu-latn locale tag — not a hack, an actual Unicode extension. Pick one deliberately and write down why; this is exactly the question your day job will ask you.

What this chapter isn't

The hreflang work is a rehearsal

Step 8 emits correct alternates and a correct canonical. No crawler will ever see them. Everything meaningful in this app sits behind authorized(), so the entire i18n SEO surface — hreflang, localised metadata, per-locale canonicals — is unreachable to Googlebot. You are learning the mechanism on a page nobody will index.

That's a fine reason to do it, as long as it stays labelled. It does not move your Phase 2 deliverable, and /ar routing on a login-walled dashboard is not a line on your CV. The value is that when you build the public project that does carry the LCP number, bilingual routing will be a solved problem you've already debugged once — including the two parts that always break, which are proxy composition and the auth path check.

The part that pays immediately is different and worth naming: your day job is an Arabic Next.js site. Steps 3 and 6 are the two places production bilingual apps actually break, and you'll have hit both here first, with nothing at stake.
