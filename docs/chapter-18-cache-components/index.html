Self-directed · Chapter 18 · Plan, second draft

Cache Components and the static shell

Every route in this app is server-rendered on demand. Eleven of eleven. Next 16's Cache Components model can turn most of that into a prerendered shell, with only the genuinely per-request parts streaming in behind it. This is the second draft of the plan, written after the first one stalled on its own step 02 for an entire session.

Before you start

Start from: the chapter-17-i18n-rtl branch. Chapter 17 is a hard prerequisite. That is unusually literal here: the first thing Cache Components does is refuse to build until [locale], the root dynamic segment Chapter 17 introduced, is given concrete values. Steps 01 and 02 exist almost entirely because of Chapter 17's i18n layer.

Terminalsetup
git checkout chapter-17-i18n-rtl
pnpm install
pnpm build   # baseline: 11 of 11 routes dynamic, only the 404 is static

What you already know after Chapter 17: routes live under app/[locale]/, i18n/routing.ts is the single source of truth for locales and slugs, navigation is imported from @/i18n/navigation, and auth is enforced in proxy.ts rather than in a callback.

What is new here: an inversion of everything the course taught about caching. Previously a route was static until something made it dynamic. Now nothing is cached unless you say so, and the build refuses to pass until every uncached read is either given a lifetime with use cache or pushed behind a <Suspense> boundary.

Where this chapter stands: steps 01 to 03 are already implemented on main. Step 03 is one edit short of its checkpoint, and finishing it is your first task. Steps 04 to 08 are designed but not implemented.

This chapter reads differently from 16 and 17

Those two are build records, written after the fact. This one is a working plan written partly ahead of the work, and it keeps its own mistakes visible rather than tidying them away: the first draft ordered its steps wrongly and stalled, and the retrospective explaining why is kept as a section. If you are reading for a clean recipe, that will feel untidy. It is deliberate, because the reason the first plan failed is the most transferable thing in the chapter.

This document was rewritten mid-build

The first draft was a reasonable-looking plan that turned out to be ordered wrong, and one of its code samples did not compile. Rather than quietly fix it, the mistake is kept and explained, because why it was wrong is the most transferable thing in this chapter. See what v1 got wrong.

Why this was rewritten

The first plan had eight steps, each with a checkpoint of the form "route X builds without error". Step 02's checkpoint was /en/login and /ar/login, and it said, in bold, to stop and finish step 02 before touching anything else.

That instruction was followed. Step 02 then took four separate fixes, each revealed only after the previous one landed:

#What the build saidWhat it actually needed
1 Cannot find name 'getFormats' The plan's own probe snippet imported a function that is not a public export. It never compiled.
2 Blocking read at i18n/request.ts, await requestLocale Locale resolution falling through to headers().
3 Unstable value new Date() at getNow() A cached build-time now in the request config.
4 useSearchParams() outside <Suspense> A boundary around a component the plan had assigned to step 06.

Item 4 is the one that broke the plan rather than merely delaying it. Step 02's checkpoint could not be reached without doing part of step 06. The steps were not independent, and the checkpoints assumed they were.

The idea the first plan was missing

The transferable finding

Prerender blockers are a stack, not a list. The build reports only the first blocker it hits on each route. Fix it and the next one appears, on the same route, with a completely different error message and often in a completely different file. A route goes green only when every blocker in its whole tree is gone.

This has two consequences that should have shaped the first plan and did not.

A route-shaped checkpoint is a late checkpoint. "Login builds clean" is not a step-02 outcome, it is the outcome of every step that touches anything login renders: the root layout, the i18n config, and every client component on the page. Putting it at step 02 guaranteed the step could not close.

Steps should be ordered by blast radius, not by subject matter. The root layout and the shared chrome are on every route, so anything blocking there blocks everything, and nothing else can be verified until they are clear. The first plan put client-hook boundaries at step 06 because they felt like a rendering concern rather than a config concern. In reality LocaleSwitcher and NavLinks render inside SideNav, which renders in the dashboard layout, which means those two components alone block all fourteen dashboard paths.

So this draft is organised in stages. Stage 1 clears everything with app-wide blast radius. Only at the end of stage 1 does the first route-shaped checkpoint appear.

Blocker taxonomy

Two error strings, two very different fixes

"encountered uncached or runtime data" means an async read that could be cached or streamed. It has three escapes: cache it, wrap it, or opt out.

"encountered the unstable value new Date()" means synchronous IO. It has no streaming escape and instant = false does not clear it. It must be cached, moved to the client, or removed. Reading the two messages as the same category costs an afternoon.

Step 02 · doneMake next-intl prerenderable

i18n/request.ts app/[locale]/layout.tsx

The root layout renders NextIntlClientProvider, so anything it blocks on blocks every route in the app. Reading the installed package shows the server provider performing five awaits before it renders:

node_modules/next-intl/.../NextIntlClientProviderServer.jsinstalled
formats:  formats  === undefined ? await getFormats()  : formats,
locale:   locale   ?? (await getLocaleCached()),
messages: messages === undefined ? await getMessages() : messages,
now:      now      ?? (await getConfigNow()),
timeZone: timeZone ?? (await getTimeZone()),

All five funnel into next-intl's getConfig(), which calls getRequestConfig in i18n/request.ts. Three separate things in that path block a prerender, and they have to be fixed together.

The one that matters: stop resolving the locale from the request

next-intl's requestLocale resolves through getRequestLocale(), which returns a cached value if setRequestLocale() populated one and otherwise falls back to reading headers(). Under prerendering the cache is not reliably populated across segment boundaries, so it reaches headers() and blocks.

The documented remedy for that is to call setRequestLocale(locale) in every page and layout that touches a next-intl API. In this app that is seven files, all of which then need their params plumbed in. Do not do that. Both requestLocale and setRequestLocale are deprecated in next-intl 4.14.1:

node_modules/next-intl/dist/types/.../getRequestConfig.d.tsinstalled
/**
 * @deprecated Please migrate to [`next/root-params`]
 */
requestLocale: Promise<string | undefined>;

Next 16 ships next/root-params, which exposes each root dynamic segment as an async getter callable from any Server Component with no prop drilling and no request read. The types are generated during next dev and next build:

.next/types/root-params.d.tsgenerated
declare module 'next/root-params' {
  export function locale(): Promise<string>
}

Reading the locale from there instead removes the entire class of failure, and setRequestLocale can be deleted from the codebase outright rather than spread to six more files.

i18n/request.tsedit
import { locale as rootLocale } from "next/root-params";

// Message files are build-time constants, so 'max' is honest. The
// dynamic import() is uncached IO, which blocked every route while it
// ran per request.
async function loadMessages(locale: string) {
  "use cache";
  cacheLife("max");
  return (await import(`../messages/${locale}.json`)).default;
}

// next-intl only needs `now` for format.relativeTime, which this app
// never calls. A live new Date() is synchronous IO the prerender rejects
// with no escape hatch, so cache a fixed build-time value instead.
async function getBuildTime() {
  "use cache";
  cacheLife("max");
  return new Date();
}

export default getRequestConfig(async () => {
  - const requested = await requestLocale;   // reaches headers()
  + const requested = await rootLocale();     // part of the route
  const locale = hasLocale(routing.locales, requested)
    ? requested : routing.defaultLocale;

  return {
    locale,
    messages: await loadMessages(locale),
    now: await getBuildTime(),
  };
});

And pass the provider its props

With the config prerenderable, hoist the remaining reads into the layout so the provider skips its own. One trap: getFormats is not a public export, only the runtime getFormatter is. Since this app configures no custom formats, an empty object satisfies the check and skips the read.

app/[locale]/layout.tsxedit

const timeZone = await getTimeZone();

// cached value in the request config resolves it instead.

<NextIntlClientProvider

Step 04Cache a read with use cache

Concept

The use cache directive, and its companion cacheLife. This is the central API of the whole feature. Everything before this step was clearing obstacles; this is the first step that actually caches anything.

Why now

Steps 01 to 03 removed every blocker that lived in shared chrome. What is left blocking is no longer framework plumbing, it is your own database reads. Six of the ten remaining paths fail for exactly one reason: a page awaits a Postgres query that Next.js has no lifetime information for, so it cannot be prerendered.

The mental model to carry in

Under Cache Components, an uncached await is not "slow", it is unprerenderable. Next.js will not guess whether a value can be reused. use cache is you telling it "this result is reusable, and here is for how long". That declaration is what lets the result be baked into the static shell.

Where

app/lib/data.ts

One file. Four exported functions inside it: fetchRevenue, fetchCustomers, fetchInvoiceById, fetchCustomerById.

Current state

app/lib/data.ts is the only module in the project that reads from Postgres. It opens a postgres client at module scope and exports ten query functions. None of them carries a cache directive today. Each currently looks like this:

app/lib/data.ts · as it exists nowcurrent
export async function fetchCustomers() {
  try {
    const customers = await sql<CustomerField[]>`
      SELECT id, name FROM customers ORDER BY name ASC
    `;
    return customers;
  } catch (err) {
    console.error("Database Error:", err);
    throw new Error("Failed to fetch all customers.");

Four of the ten are safe to cache right now. The other six are not, and the reason why is step 05. What makes these four special is that none of them reads request state: no getLocale(), no cookies, no headers. Check for yourself before you edit:

What to change

Add the import at the top of the file:

Then add a directive and a lifetime as the first two statements in each of the four function bodies, above the existing try. The directive must be the first statement in the body, exactly like "use client" at the top of a file.

  try {

  }

  }

Do the same for fetchRevenue ("max") and fetchCustomerById ("minutes"). Do not change any query, any return value, or any error handling.

Optional cleanup while you are in there

fetchInvoiceById has a stray console.log(invoice) left over from the course. Caching means it will now fire only on a cache miss rather than every request, which makes it more confusing than useful. Deleting it is reasonable and unrelated to the lesson.

Why this change works

Two mechanisms are worth understanding, because step 05 depends on both.

The lifetime is what makes prerendering possible. A use cache scope without cacheLife silently gets the default profile. The official docs recommend always pairing them so the behaviour is readable at the call site, and it matters more than style: a profile with a very short stale (under 30 seconds) is treated as short-lived and is excluded from the prerender, becoming a dynamic hole instead. Naming the profile is how you stay in control of that.

Arguments become the cache key. fetchInvoiceById("abc") and fetchInvoiceById("def") are two separate entries. From the docs: the key is built from the build ID, a hash of the function's identity, and its serializable arguments. Values captured from an enclosing function scope get bound in as arguments too. This is the single most important property to internalise, and step 05 is entirely about its consequences.

Expect a regression here. It is the point of step 06.

Once fetchInvoiceById is cached, editing an invoice and returning to its edit form may show you the old amount for up to a minute. You have not broken anything. The existing revalidatePath("/[locale]/dashboard/invoices", "page") calls in app/lib/actions.ts name the list route, not the edit route, so they do not clear this new entry. Step 06 fixes it properly with tags. Notice the staleness now so that step 06 solves a problem you have actually felt.

Checkpoint

Specifically, all six of these clear: /en and /ar variants of /dashboard/invoices/create, /dashboard/invoices/[id]/edit, and /dashboard/customers/[id]/edit. The only routes still failing are the two list pages. If a route you expected to clear is still failing, read the frame in the error: it will name the function you missed.

Learning takeaway

A cached function is a promise you make to the framework: this output is reusable for this long. In exchange, its result can live in the static shell instead of costing a query per request. The promise is only safe when the output genuinely does not depend on who is asking, which is exactly the constraint step 05 runs into.

Step 05The request-data wall, and what cache keys cost

Concept

Why a plain use cache scope cannot read request data, and why putting request-shaped values into a cache key is expensive even when it is legal. This is where Chapter 17's bilingual work collides with Chapter 18's caching model, and the collision is the lesson.

Why now

You just cached four functions. Try to cache a fifth, fetchCardData, the same way. It will not work, and the reason is not a bug. This step is about understanding the wall rather than working around it.

Where

app/lib/data.ts app/lib/definitions.ts app/ui/dashboard/cards.tsx app/ui/dashboard/latest-invoices.tsx app/ui/customers/table.tsx

Current state

Three functions in app/lib/data.ts call getLocale() so they can format money before returning it. fetchCardData is representative:

app/lib/data.ts · as it exists nowcurrent
export async function fetchCardData() {
  try {
    const locale = await getLocale();
    // ...three parallel COUNT / SUM queries...

    return {
      numberOfCustomers,
      numberOfInvoices,
      totalPaidInvoices: formatCurrency(data[2][0].paid ?? "0", locale),
      totalPendingInvoices: formatCurrency(data[2][0].pending ?? "0", locale),
    };
  } catch (error) { /* ... */ }
}

Chapter 17 introduced this. It was flagged at the time as a known gap, on tidiness grounds: formatting is a presentation concern and it had drifted into the data layer. Under Cache Components it stops being a matter of taste and becomes a hard blocker.

Try it first, then read on

Before making the real change, add "use cache" and cacheLife("minutes") to fetchCardData exactly the way you did in step 04, and run pnpm build. Read the error. Then undo it. Seeing the failure yourself is worth more than being told about it.

What you are seeing

getLocale() resolves through next-intl's request configuration, which is per-request state. A plain use cache scope runs in an isolated environment that has no access to the incoming request, by design: if it could read the request, its output could differ per request, and then it would not be safe to reuse. The restriction is what makes the cache correct.

The two ways out, and why they are not equal

Option A: hoist the locale and pass it in as an argument. This is legal and is the documented pattern for feeding runtime values into cached functions. The caller reads the locale outside the cached scope and passes it down:

Option A · legal, but think about the costreference
export async function fetchCardData(locale: string) {
  "use cache";
  cacheLife("minutes");
  // locale is now part of the cache key
}

The cost is in that last comment. Arguments become the cache key, so fetchCardData("en") and fetchCardData("ar") are two entries, running two identical COUNT queries, storing two copies of the same numbers, differing only in how they were rendered as text. Your hit rate halves for no gain. Add a third locale later and it thirds.

Option B: return raw values and format in the component. The data layer returns what Postgres returned. The component formats at render time, where it already has a locale for free.

Take option B

One cache entry serves every locale, because the cached value is genuinely locale-independent: it is a number. The Chapter 17 gap closes as a side effect. And the general rule it teaches transfers well beyond i18n: anything request-shaped that you bake into a cached value multiplies your entry count by the cardinality of that thing. Currency, timezone, per-user labels and A/B buckets all behave identically.

What to change

Good news on types: the raw and formatted shapes both already exist in app/lib/definitions.ts from the original course. You are moving between two types that are already written, not inventing any.

Do not reflexively cache the search queries

Knowing what not to cache is half of using this feature well.

Why this change works

After the refactor the cached value is a set of numbers, which is the same in every locale. The locale never enters the cache key, so /en and /ar share one entry. Formatting still happens per request, but it is pure CPU on an already-loaded value, not a database round trip, and it happens in the component that already knows the locale.

Step 06Invalidation: cacheTag and updateTag

Concept

cacheTag to label cached data, and updateTag to expire it after a mutation. Plus the distinction between the three invalidation APIs, which is the part most people get wrong.

Why now

Because you have a bug, and you put it there in step 04. Caching a read without a way to invalidate it means every mutation in the app is now capable of showing stale data. Correctness before more optimisation.

Where

app/lib/data.ts app/lib/actions.ts

Current state

app/lib/actions.ts is the only module that writes to Postgres. It invalidates with six calls that all take this shape:

app/lib/actions.ts · as it exists nowcurrent
revalidatePath("/[locale]/dashboard/invoices", "page");
redirect({ href: "/dashboard/invoices", locale: await getLocale() });

They appear in createInvoice, updateInvoice, deleteInvoice, createCustomer, updateCustomer and deleteCustomer. This still works, and Chapter 17's trick of using the literal [locale] segment so both locales invalidate at once still works too. But it names a route, and your new cache entries are keyed by data. Editing an invoice revalidates the list route while fetchInvoiceById(id), which backs the edit form, keeps its entry.

What to change

1. Tag the reads in app/lib/data.ts. Import cacheTag alongside cacheLife, then add one tag call inside each cached scope. Use two coarse tags, "invoices" and "customers":

app/lib/data.tsedit
import { cacheLife, cacheTag } from "next/cache";

export async function fetchInvoiceById(id: string) {
  "use cache";
  cacheTag("invoices");
  cacheLife("minutes");
  // ...
}
FunctionTag
fetchInvoiceById, fetchLatestInvoicesinvoices
fetchCustomerById, fetchCustomerscustomers
fetchCardDataboth, call cacheTag twice
fetchRevenuenone, it is seed data nothing mutates

fetchCardData takes both tags because its totals move when either table changes. cacheTag accepts multiple calls in one scope.

2. Swap the invalidation in app/lib/actions.ts. Replace each revalidatePath with updateTag naming the table the action touched:

app/lib/actions.tsedit
- import { revalidatePath } from "next/cache";
+ import { updateTag } from "next/cache";

  // ...inside updateInvoice, and the five sibling actions...
- revalidatePath("/[locale]/dashboard/invoices", "page");
+ updateTag("invoices");
  redirect({ href: "/dashboard/invoices", locale: await getLocale() });

Use updateTag("invoices") in the three invoice actions and updateTag("customers") in the three customer actions. Note that deleteCustomer can return early with a refusal when the customer still has invoices; only call updateTag on the path where a delete actually happened.

You will find a bug while doing this, and it makes the argument for you

Look at deleteCustomer, at app/lib/actions.ts line 270. It calls:

app/lib/actions.ts · the bugcurrent
await sql`DELETE FROM customers WHERE id = ${id}`;
// ...
revalidatePath("/[locale]/dashboard/invoices", "page");   // wrong route

It deletes a customer and then revalidates the invoices route. The customers list is never invalidated, so a deleted customer can linger there. This predates Chapter 18 and has nothing to do with caching, but it is the sharpest possible argument for tags: the path is a string that has to be kept in sync with a route tree by hand, and nothing type-checks it, so it silently drifted. updateTag("customers") in a function called deleteCustomer is a much harder mistake to make. Converting this call fixes the bug as a side effect.

Why this change works, and why updateTag specifically

There are three invalidation APIs and they are not interchangeable. This is the table worth remembering:

APIWhere it may be calledBehaviourRight for
updateTag(tag) Server Actions only Expires immediately; the next request waits for fresh data Read-your-own-writes
revalidateTag(tag, profile) Actions and Route Handlers Stale-while-revalidate; serves the old value while refreshing Webhooks, background events
revalidatePath(path) Anywhere Drops everything for a route When you do not know the tags

Every mutation in this app is a user editing their own data and then being redirected to look at it. That is the textbook read-your-own-writes case, so updateTag is correct. revalidateTag would be actively wrong here: it serves the stale value while refreshing behind the scenes, so the user would submit an edit, get redirected, and see their old amount looking back at them. Note also that revalidateTag now requires a cache profile as its second argument.

Tags and keys are stored in plain text

Neither cache keys nor tag names are hashed. A cached function's arguments are serialized straight into its key, and cacheTag values are stored as written. Tag on stable identifiers only. Never put an email address, a token, or anything personal in a tag or in a cached function's arguments.

Checkpoint

Checkpoint This one is behavioural, not a build check. With pnpm dev running and logged in, edit an invoice's amount, submit, and let it redirect you to the list. The new amount must be there immediately. Then open that invoice's edit form again: the new amount must be there too, which is the case that was broken after step 04. Do it once in /en and once in /ar. Also confirm the dashboard cards update after creating an invoice, which is what the double tag on fetchCardData buys you.

Learning takeaway

Caching a read is only half a feature; the other half is deciding how it becomes wrong and who is responsible for noticing. Tags let you describe invalidation in terms of the data that changed rather than the URLs that happen to display it, which is both more precise and more durable when routes get renamed.

Step 07Streaming what genuinely cannot be cached

Concept

Runtime APIs, searchParams in particular, and the "push the dynamic read down" pattern. The counterpart to use cache: what to do with data that is legitimately different on every single request.

Why now

Four paths are still failing, and no amount of caching will fix them. A search result depends on a URL that does not exist until someone types into the box. This is the case Cache Components answers with streaming rather than caching, and it is the last blocker in the app.

Where

app/[locale]/dashboard/invoices/page.tsx app/[locale]/dashboard/customers/page.tsx

Current state

Both list pages have the same shape. Using the invoices one:

app/[locale]/dashboard/invoices/page.tsx · as it exists nowcurrent
export default async function Page(props: {
  searchParams?: Promise<{ query?: string; page?: string }>;
}) {
  const t = await getTranslations("Invoices");
  const searchParams = await props.searchParams;   // the whole page waits here

  const query = searchParams?.query || "";
  const currentPage = Number(searchParams?.page) || 1;
  const totalPages = await fetchInvoicesPages(query);

  return (
    <div className="w-full">
      <h1>{t("title")}</h1>
      <Search placeholder={t("search")} />
      <Suspense key={query + currentPage} fallback={<InvoicesTableSkeleton />}>
        <Table query={query} currentPage={currentPage} />
      </Suspense>
      <Pagination totalPages={totalPages} />
    </div>
  );
}

Note that there is already a Suspense boundary around the table, added during the original course. It is not enough, and the reason is precise: await props.searchParams happens at the top of the page component, above the boundary. Everything below it, heading included, waits on a value that only the heading does not need.

What to change

Stop awaiting the promise and start passing it. The page component becomes synchronous in its dynamic parts; a child inside a boundary does the awaiting.

app/[locale]/dashboard/invoices/page.tsxedit
export default async function Page(props: {
  searchParams?: Promise<{ query?: string; page?: string }>;
}) {
  const t = await getTranslations("Invoices");
  // no await on searchParams here any more

  return (
    <div className="w-full">
      <h1>{t("title")}</h1>
      <Search placeholder={t("search")} />

      <Suspense fallback={<InvoicesTableSkeleton />}>
        <InvoicesResults searchParams={props.searchParams} />
      </Suspense>
    </div>
  );
}

async function InvoicesResults({ searchParams }: {
  searchParams?: Promise<{ query?: string; page?: string }>;
}) {
  const params = await searchParams;              // awaited inside the boundary
  const query = params?.query || "";
  const currentPage = Number(params?.page) || 1;
  const totalPages = await fetchInvoicesPages(query);

  return (
    <>
      <Table query={query} currentPage={currentPage} />
      <div className="mt-5 flex w-full justify-center">
        <Pagination totalPages={totalPages} />
      </div>
    </>
  );
}

Move Table and Pagination together into the new child, since both need the resolved params. The old inner Suspense key={query + currentPage} wrapper around Table becomes redundant once the outer boundary is keyed by nothing but the request; you can drop it. Apply the identical transformation to the customers page, which uses CustomersTable, fetchCustomersPages and CustomersTableSkeleton.

Push the read down, do not wrap the world

It is tempting to wrap the entire page body in one boundary and move on. That builds, and it throws away most of the benefit, because everything inside a boundary leaves the static shell. The useful version keeps the boundary as small as the set of components that genuinely need the URL. Here the heading and the search input stay outside it and ship in the shell.

Why this change works

A promise is not a blocking read until something awaits it. Passing props.searchParams down as a prop hands the obligation to await into a subtree that Next.js is allowed to render later. The page above it has no request dependency left, so it prerenders; the child streams in when the request arrives and the URL is finally known.

The same rule governs the client hooks you dealt with in step 03. useSearchParams can never resolve at build time, which is why it always needs a boundary. Server-side searchParams and client-side useSearchParams are the same constraint wearing different clothes.

Learning takeaway

Cache Components gives you two tools, not one. use cache for anything reusable, <Suspense> for anything genuinely per-request, and the skill is telling the two apart honestly. Reaching for a cache on a search result would have been the wrong instinct even though it compiles.

Cache Components has a wider surface than this chapter uses. These were considered and left out on purpose, because forcing them into this app would have meant writing code that exists only to exercise an API. Each is worth knowing about even without implementing it here.

On the missing session read

This is worth dwelling on, because it is a genuine architectural consequence rather than a gap in the exercise. Chapter 17 put the auth check in proxy.ts deliberately, after two bypasses proved that the authorized() callback was not being enforced. A middleware-level guard means no page ever calls auth(), which in turn means no page has a cookie read to prerender around. The dashboard's static shell is therefore larger than it would be in an app that checks the session inside the layout. An architectural decision made for security reasons paid off again, for performance reasons, two chapters later.

If you want to see use cache: private in practice, the pattern is: resolve the user inside a private scope, then pass only the user id into a plain cached function. The session stays browser-only while the data it points at caches on the server under a key that is just an id. Keep the inner function unexported so no caller can pass someone else's id.

The escape hatch, and when using it is correct

any page, layout or defaultreference
export const instant = false;

It marks a segment as allowed to block. Three things it does not do:

  • It does not force the route dynamic. A route that can still prerender a shell will ship one.
  • It does not silence synchronous IO errors. new Date(), Math.random() and crypto.randomUUID() still fail the build, opted out or not.
  • It does not change runtime behaviour. An offending route returns 200 with correct HTML in dev either way; insights appear only in the overlay and the dev-server log.

Using it on a blocker you understand and are deferring is fine. Using it to turn the build green without reading the error wastes the entire feature.

What the first draft got wrong

Four mistakes, one of them structural

It shipped code that did not compile. Step 02's probe imported getFormats from next-intl/server. That function exists in the package, but only as an internal module: the public barrel exports getFormatter, not getFormats. The plan was written from reading next-intl's source without checking what the entrypoint actually re-exports. One node -e "Object.keys(require('next-intl/server'))" would have caught it.

It recommended the deprecated API. The whole step 02 bisection was built around making setRequestLocale work under prerendering, and its worst-case branch was "spread it to every page". The installed package marks both it and requestLocale deprecated, pointing at next/root-params, which is a one-file change that removes the problem instead of distributing it. The deprecation notice was visible in the editor the whole time and got read as noise.

It assumed the first error was the only error. Step 02 was scoped to two files. Clearing it actually took four fixes across three concerns, because the build only ever names the first blocker per route. A step scoped by file list is a guess; a step scoped by error class is checkable.

And the structural one: it ordered steps by subject, not by blast radius. Client-hook boundaries were step 06 because they read like a rendering topic. But LocaleSwitcher renders in the sidebar and on both public pages, so it alone blocked all sixteen remaining paths. A step-02 checkpoint that depended on step 06 could never pass. Ordering by how many routes a fix unblocks, rather than by which part of the app it belongs to, is the correction this draft is built on.

The through-line is the same one chapter 17 ended on, in a new costume: the plan was written by reading, and reality was found by running. Chapter 17 learned that about auth bypasses. This chapter learned it about the plan itself.

What this chapter isn't

A static shell on a login wall has a ceiling

Almost everything here sits behind authentication. A session read cannot be prerendered, so on the dashboard routes the shell is the chrome: the sidebar frame, the headings, the skeletons. The numbers, tables and charts still cost a request. That is a real improvement to perceived load, and it is not a static site.

The routes that gain most are the two nobody looks at: login and home. Which is a fair description of this app's whole SEO story, already said plainly in chapter 17.

What makes it worth doing is that the model is where the framework has committed, and it is genuinely inverted from what the course taught. Learning it on eleven routes with a bilingual layer and an auth guard already in place beats learning it on a blog, because the awkward parts, a provider in the root layout, a switcher in the shared chrome, formatting that leaked into the data layer, are what a real app has and a tutorial does not.

And the headline is a build-output diff, not a performance claim. The performance claim needs a deployed build and a throttled measurement. That is the next chapter.
