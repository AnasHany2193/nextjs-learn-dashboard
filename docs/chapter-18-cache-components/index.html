Self-directed · Chapter 18 · Plan

Cache Components and the static shell

Every route in this app is server-rendered on demand. Eleven of eleven. Next 16's Cache Components model can turn most of that into a prerendered shell that ships instantly, with only the genuinely per-request parts streaming in behind it. This is the plan for getting there, written after a reconnaissance run that already found the one thing blocking all eleven.

What this chapter should produce

  • cacheComponents: true on Next.js 16.3.3
  • A non-empty static shell for every route that can have one
  • use cache and cacheLife on the read paths in app/lib/data.ts
  • cacheTag plus updateTag replacing six blanket revalidatePath calls
  • The Chapter 17 known gap (formatting inside the data layer) closed, because it becomes a hard blocker here
  • A before and after route table, which is the actual deliverable

Why this chapter, and why now

Chapter 17 moved every route under app/[locale]/. Drawing cache boundaries before that would have meant drawing them twice, so this waited. Now the route tree is stable and the boundaries can be drawn once.

The premise of Cache Components is a reversal. In the old model, a route was static until something made it dynamic, and a single cookies() call anywhere in the tree quietly cost you the whole page. In the new model nothing is cached unless you say so, and the framework refuses to build until every uncached read is either wrapped in use cache or pushed behind a <Suspense> boundary. The compiler stops guessing and starts asking.

That is a better fit for a learning repo than for a deadline: the build failures are the lesson. So the working method for this chapter is to enable the flag first, read what breaks, and let the error list write the step order.

Terminology, because the docs assume it

The static shell is the part of a route's HTML that can be produced at build time, with holes where the dynamic parts go. A visitor gets the shell immediately from the edge; the holes fill in from the server as they stream. This is what used to be called Partial Prerendering. In Next 16 the experimental_ppr flag is gone and PPR is simply what Cache Components does.

Eighteen paths, which is nine routes across two locales, and a single cause. NextIntlClientProvider sits in the root layout, so whatever it does, every route inherits. Reading the installed package explains it. The server version of the provider performs five awaits before it renders anything:

node_modules/next-intl/.../NextIntlClientProviderServer.jsinstalled

All five funnel into next-intl's getConfig(), which calls getRequestConfig from i18n/request.ts. That file does a dynamic import() of the message JSON, and a dynamic import is uncached IO. So the root layout performs uncached IO on every render, and under Cache Components that is fatal to the shell.

The obvious move is to cache the message import, which was tried:

This is the chapter's real risk

Steps 03 to 08 are ordinary work with known shapes. Step 02 is load-bearing and unresolved: if next-intl 4.14.1 simply cannot render its provider inside a prerender, the ceiling for this chapter drops from "most routes get a shell" to "the flag is on and routes opt out". That outcome is worth writing down too, but it should be discovered in step 02, not in step 08.

Decisions, and what they cost

Adopt directly, not incrementally

The migration guide offers instant = false on every segment as a way to get the app building immediately and convert routes one at a time. For an eleven-route app that is more bookkeeping than benefit, and it hides exactly the errors this chapter exists to read. Direct adoption, with instant = false kept as a deliberate escape hatch (see the escape hatch) rather than a starting position.

Cache in the data layer, not in the pages

Every database read already goes through app/lib/data.ts. Putting use cache on those functions means one place to reason about lifetimes, and it keeps the pages readable. The alternative, caching whole page components, couples the cache key to the route and makes the same query cached twice under two different keys.

Plain use cache, not use cache: remote

Plain use cache stores entries in memory. On serverless that means they die with the instance and do not survive a deployment. use cache: remote gives durable shared storage and is the correct production answer, but it needs a cache handler this project does not have and will not pay for. Using the in-memory default and saying so plainly is better than pretending the hit rate is production-grade.

Worth knowing before you migrate anything

The old fetch Data Cache and unstable_cache both persisted across deployments and across serverless instances. Plain use cache does not. Migrating a hot unstable_cache path to use cache without a cache handler is a downgrade in persistence, even though it looks like a modernisation.

Keep the login page honest

The login page has no user-specific content and should end up fully static. If it does not, something is wrong with step 02, and it is the cheapest possible test case. It becomes the canary for the whole chapter.

next.config.ts app/[locale]/layout.tsx

Then give [locale] its two values. routing.locales is already the single source of truth from Chapter 17, so this stays derived rather than becoming a third list to keep in sync.

app/[locale]/layout.tsxedit

// it can prerender a shell and check the shell is non-empty. Returning
// [] now errors instead of deferring every path to the first visit.

  return routing.locales.map((locale) => ({ locale }));

Locales are not the same as ids

There are exactly two locales, so listing both is complete. For [id] routes the rule is different: return a subset, often just one, and let the rest render on request. Paths not returned are still served, they just do not get a prebuilt shell. Do not try to enumerate every customer id.

Step 02Unblock the root layout

i18n/request.ts app/[locale]/layout.tsx

This is the step that decides the chapter. From recon, the provider performs five request-config reads and caching the message import alone did not clear the error. So work it as a bisection, not as a guess.

Bisect: pass every prop explicitly

Each of the five awaits is skipped when the corresponding prop is supplied. Hoist all five into the layout so the failing one names your line instead of the provider's:

app/[locale]/layout.tsxprobe
// Temporary. Whichever await blocks will now point here, and
// --debug-prerender will name the line instead of the provider.
const messages = await getMessages();
const timeZone = await getTimeZone();
const formats  = await getFormats();
const now      = await getNow();

return (
  <NextIntlClientProvider
    locale={locale} messages={messages} timeZone={timeZone}
    formats={formats} now={now}
  >
    {children}
  </NextIntlClientProvider>
);

Run pnpm build --debug-prerender and read which line it names. Then remove the probes one at a time to find the minimum set that has to be passed explicitly.

The three shapes the answer can take

If the blocker isThenCost
Only the message import Cache loadMessages with cacheLife('max') and pass messages in explicitly, so the provider skips its own read None. Messages are build-time constants.
getTimeZone(), via Intl.DateTimeFormat().resolvedOptions() Pass a fixed timeZone string rather than letting it resolve from the environment You must pick one. Server default is not a real answer anyway.
getRequestLocale() reaching headers() setRequestLocale(locale) already runs before the provider, so this should be populated from cache. If it is not, the ordering is wrong or the React cache is not shared with the prerender. Investigation. This is the bad outcome.
Why now is the awkward one

now: now ?? (await getConfigNow()) awaits whenever the prop is undefined, and you cannot supply a real value without calling new Date(), which is exactly the synchronous IO the prerender rejects. If now turns out to be the blocker, the fix is to set a now in the request config so getConfigNow() resolves from cached config rather than to pass one from the layout.

Step 03Get the locale out of the data layer

app/lib/data.ts app/ui/dashboard/cards.tsx app/ui/dashboard/latest-invoices.tsx app/ui/customers/table.tsx

Chapter 17 closed with a known gap: currency and date formatting live inside app/lib/data.ts, which is why three data functions call getLocale(). That was a tidiness complaint then. Under Cache Components it is a hard blocker, because a plain use cache function may not read request state, and getLocale() is request state.

app/lib/data.tscurrent
export async function fetchCardData() {
  const locale = await getLocale();          // blocks "use cache"
  ...
  totalPaidInvoices: formatCurrency(data[2][0].paid ?? "0", locale),
}

There are two ways out, and they are not equivalent.

Option A: pass the locale in as an argument

Legal, and the pattern the docs describe for runtime values. The caller reads the locale outside the cached scope and passes it down, where it becomes part of the cache key. It also means two cache entries for one query, one per locale, holding identical numbers formatted differently.

Option B: return raw numbers, format in the component

The data layer returns what the database returned. The component formats at render time, where it already has a locale. One cache entry serves both locales, the query result stops being locale-shaped, and the Chapter 17 gap closes on its own.

app/lib/data.tsplanned
// Raw cents out. No getLocale(), no formatting, so the cache key is
// the query alone and /en and /ar share one entry.
export async function fetchCardData() {
  "use cache";
  cacheLife("minutes");
  ...
  return { numberOfCustomers, numberOfInvoices,
           totalPaid, totalPending };   // numbers, not strings
}

Take option B. Formatting is a presentation concern that drifted into the data layer during the course, and this is the forcing function to put it back. Three data functions lose their getLocale() call; the components that render their output gain a formatCurrency(value, locale).

The transferable idea

Anything locale-shaped, user-shaped or request-shaped that you bake into a cached value multiplies your cache entries by the cardinality of that thing. Formatting inside a cached query does not just read badly, it halves the hit rate. This generalises well past i18n: currency, timezone, and per-user labels all behave the same way.

One thing that looks like a blocker and is not

formatDateToLocal calls new Date(dateStr). The prerender rejects new Date() with no arguments, because it reads the clock. Constructing a Date from a fixed string is deterministic and fine. Likewise the new Date() in createInvoice is inside a Server Action, which only ever runs at request time and is never prerendered.

Checkpoint grep -rn "getLocale" app/lib/data.ts returns nothing, and the dashboard still shows Arabic-Indic digits under /ar.

Step 04use cache and a deliberate cacheLife

app/lib/data.ts

With the locale gone, the read functions become cacheable. Each gets the directive and an explicit lifetime. The docs recommend always calling cacheLife rather than letting default apply silently, and that matters more once scopes nest.

Profilestalerevalidateexpire
default5 min15 minnever
seconds30 s1 s1 min
minutes5 min1 min1 hour
hours5 min1 hour1 day
days5 min1 day1 week
max5 min30 days1 year

The three properties answer three different questions. stale is how long the browser's router reuses what it has without asking. revalidate is how long before the server refreshes in the background while still serving the old value. expire is when the server stops serving the old value at all and the next request waits.

Proposed assignment, chosen from how often each thing actually changes in this app:

FunctionProfileBecause
fetchRevenuemaxTwelve rows of seed data that have never changed
fetchCardDataminutesAggregates that move whenever an invoice is written
fetchLatestInvoicesminutesSame, and visibly wrong if stale for long
fetchCustomershoursDropdown options for the invoice form
fetchInvoiceById, fetchCustomerByIdminutesEdit forms, must not show a stale amount
fetchFilteredInvoices, fetchFilteredCustomersminutesKeyed by query and page, so each combination caches separately
Do not cache the search results reflexively

The filtered queries take query and currentPage, and both become part of the cache key. A search box that fires per keystroke will mint a cache entry per prefix the user typed. It is bounded in a demo and unbounded in production. If the entry count looks silly, the right answer is to leave these two uncached and let them stream, which is what the Suspense boundary in step 06 is for.

Step 05Tags, and telling the two invalidation APIs apart

app/lib/data.ts app/lib/actions.ts

The app currently invalidates with six calls that all look like this:

app/lib/actions.tscurrent
revalidatePath("/[locale]/dashboard/invoices", "page");

That works and keeps working. It is also a blunt instrument: it names a route, so editing one invoice throws away the cached data for the customers page too if they happen to share a segment, and it says nothing about what changed. Tags name the data instead.

app/lib/data.tsplanned
export async function fetchFilteredInvoices(query: string, page: number) {
  "use cache";
  cacheTag("invoices");
  cacheLife("minutes");
  ...
}

Then the choice of invalidation API, which is the part worth learning properly:

APIBehaviourUse when
updateTag(tag) Expires the tag so the next request waits for fresh data The user just made this change and must see it. Server Actions only.
revalidateTag(tag, profile) Serves the stale value while refreshing behind it A webhook or background event. The profile argument is now required.
revalidatePath(path) Unchanged from the old model You want a whole route gone, tags or not

Every invalidation in this app happens right after the user edited something, so all six become updateTag. Read-your-own-writes is exactly the case it exists for: with revalidateTag the user would submit the edit form, get redirected, and see their old value staring back while the refresh happened behind them.

app/lib/actions.tsplanned
- revalidatePath("/[locale]/dashboard/invoices", "page");
+ updateTag("invoices");
  redirect({ href: "/dashboard/invoices", locale: await getLocale() });
Tags are stored in plain text

Cache keys and tag names are not hashed. A cached function's arguments are serialised straight into its key, and cacheTag values are stored as written. Tag on stable identifiers. Never put an email, a token or anything personal in a tag or in a cached function's arguments.

Checkpoint Edit an invoice amount, submit, and land on the list with the new amount already showing. Not the old one, not a flash of the old one.

Commit

refactor(actions): replace revalidatePath with tagged cache invalidation

Tag the cached queries with cacheTag and invalidate by tag instead of by

than they had to and said nothing about what had changed.

Every invalidation here follows a user edit, so all six become updateTag
rather than revalidateTag: updateTag makes the next request wait for fresh

Step 06Push searchParams behind Suspense

app/[locale]/dashboard/invoices/page.tsx app/[locale]/dashboard/customers/page.tsx

Both list pages await searchParams at the top of the component. Search params are only knowable at request time, so awaiting them there means the entire page waits, including the heading and the search box that do not depend on them at all.

app/[locale]/dashboard/invoices/page.tsxcurrent
export default async function Page(props: {...}) {
  const searchParams = await props.searchParams;   // whole page waits
  const query = searchParams?.query || "";
  const totalPages = await fetchInvoicesPages(query);
  ...
}

The fix is to stop awaiting and start passing. The promise goes down into a child that sits inside a boundary, and the await happens there:

app/[locale]/dashboard/invoices/page.tsxplanned
export default function Page(props: {...}) {
  return (
    <div className="w-full">
      {/* heading and search box prerender into the shell */}
      <h1>{t("title")}</h1>
      <Search placeholder={t("search")} />

      <Suspense fallback={<InvoicesTableSkeleton />}>
        <InvoicesResults searchParams={props.searchParams} />
      </Suspense>
    </div>
  );
}

async function InvoicesResults({ searchParams }) {
  const { query, page } = await searchParams;   // awaited inside
  ...
}

The same rule applies on the client. useSearchParams always needs a boundary, because its value never exists at build time. This app calls it in four client components: search.tsx, pagination.tsx, login-form.tsx and locale-switcher.tsx. Each will need a boundary or will need the read pushed into a smaller leaf, and login-form.tsx is the one that matters, because it is what keeps the canary route from going fully static.

Push the read down, do not wrap the world

The temptation is to wrap the largest component in <Suspense> and move on. That works and throws away most of the benefit, because everything inside the boundary leaves the shell. The useful version is to move the read into the smallest component that genuinely needs it, so the boundary stays small.

Step 07The session read, and use cache: private

app/ui/dashboard/sidenav.tsx app/[locale]/dashboard/layout.tsx

This is where a login-walled app differs from the blog examples in the docs. A session read is a cookie read, so it can never be in the static shell. It always streams. The question is only how much of the page it drags with it.

SideNav is rendered by the dashboard layout and awaits getLocale() and getTranslations() at its top level. A top-level await in a layout holds the whole segment, {children} included, behind that request. Whatever the page below was going to prerender, it now cannot.

app/[locale]/dashboard/layout.tsxplanned
<div className="w-full flex-none md:w-64">
  <Suspense fallback={<SideNavSkeleton />}>
    <SideNav />
  </Suspense>
</div>
<div className="grow p-6 md:overflow-y-auto md:p-12">{children}</div>

For anything derived from the session there is a third directive worth knowing:

use cacheuse cache: private
Can read cookies() / headers()NoYes
Can read searchParamsNoYes
Can call connection()NoNo
Stored on the serverYesNever
Survives a page reloadYesNo, browser memory only
In the static shellYesNo, runs every render

The shape the docs recommend, and the one to follow here: resolve the user inside a private scope, then pass only the id into a plain cached function. The session read stays private and browser-only; the data it points at gets cached on the server under a key that is just an id.

the patternreference
export async function getCurrentUser() {
  "use cache: private";          // may read cookies()
  const { userId } = await getSession();
  if (!userId) redirect("/login");   // throws, so never cached
  return { id: userId };
}

export async function getNotes() {
  const user = await getCurrentUser();
  return getNotesByUserId(user.id);  // id only, not the session
}

async function getNotesByUserId(userId: string) {
  "use cache";                      // server-side, keyed by id
  cacheTag(`notes:${userId}`);
  cacheLife("minutes");
  ...
}
Keep the inner function unexported

getNotesByUserId is not exported on purpose. If it were, any caller could pass someone else's id and read their data. Resolving the user inside the exported wrapper is the thing that makes the id safe to trust.

This app does not currently fetch anything per-user (every invoice belongs to the one demo account), so step 07 is mostly about the SideNav boundary. The private-cache pattern is written down here because it is the piece that generalises, and because the next app will need it.

The escape hatch, and when using it is correct

Any segment can decline validation:

any page, layout or defaultreference
export const instant = false;

It marks a segment as allowed to block. Three things it does not do, all of which are easy to assume:

  • It does not force the route to be dynamic. A route that can still prerender a shell will still ship one.
  • It does not silence synchronous IO errors. new Date(), Math.random() and crypto.randomUUID() during prerender still fail the build, opted out or not.
  • It does not hide anything at runtime. An offending route returns 200 with correct HTML in dev either way; validation insights only appear in the dev overlay and the dev-server log, never in the response.

Using it on a route whose blocker is understood and deliberately deferred is fine. Using it to make the build go green without reading the error is how the whole feature gets wasted.

Commit discipline

Every step above ends with its own commit message, written out in full at the point you would use it. The rule for this chapter is one step, one commit, and the trigger is the checkpoint: if the checkpoint passes, commit before starting the next step.

03refactor(data): move currency and date formatting out of the data layer

Why eight and not one

Chapter 17 shipped as two commits because none of it was committed incrementally, and the write-up had to admit it: every RTL pass, translation and typed-href fix flattened into a single 45-file diff that nobody could review. This chapter is committed as it goes so that does not happen again.

Step 03 earns its own commit twice over. It touches the data layer and four components, and it is the one change here worth keeping even if Cache Components were abandoned entirely, so it should be revertible without taking the caching work with it.

Steps that may not produce a commit

Step 02 is a bisection, so it may end in build(cache): opt the root layout out of instant validation instead of a fix. Step 04 may end with the filtered queries deliberately left uncached. Either way the commit body records the decision and the reason, because a step that changed nothing still produced a finding.

What this chapter isn't

A static shell on a login wall has a ceiling

Almost everything in this app sits behind authentication. A session read cannot be prerendered, so on the dashboard routes the shell is the chrome: the sidebar frame, the headings, the skeletons. The numbers, the tables and the charts still cost a request. That is a genuine improvement to perceived load, and it is not the same as a static site.

The routes that stand to gain most are the two nobody looks at: the login page and the home page. Which is a fair description of the whole app's SEO story, and was already said plainly in Chapter 17.

What makes this chapter worth doing anyway is that the model is the direction the framework has committed to, and it is genuinely inverted from what the course taught. Learning it on eleven routes with a bilingual layer and an auth guard already in place is a better exercise than learning it on a blog, because the awkward parts, a provider in the root layout, a session read in a shared sidebar, formatting that leaked into the data layer, are the parts a real app has and a tutorial does not.

And the honest headline is a build-output diff, not a performance claim. The performance claim needs a deployed build and a throttled measurement, and that is the next chapter.
